# 需求规格（FR / NFR）

编号规则：`FR-<模块>-<序号>` 功能需求，`NFR-<类别>-<序号>` 非功能需求。
**期次**列：V1 = 首个 Android 包必须交付；V2+ = 后续，但架构需留口。
每条需求都必须可验收；「验收标准」列写的是测试用例要断言的东西。

## 1. 任务模型 FR-TASK

| 编号 | 需求 | 期次 | 验收标准 |
|---|---|---|---|
| FR-TASK-01 | 创建**单项任务**：标题、可选描述、计划时间段、分类、优先级 | V1 | **单事项必须有开始与结束**（默认已给：开局是**全天 + 今天**；关掉全天则补「下一个整点 + `behavior.defaultDuration`」）；**临时事项仅填标题即可保存**；其余字段留空时用配置中心默认值。见 §1.1 |
| FR-TASK-02 | 创建**阶段事项**：一个任务包含 2..N 个有序阶段，每阶段有独立标题、时间段、完成状态 | V1 | 阶段可增删改、可拖拽重排；父任务进度 = 已完成阶段数 / 总阶段数 |
| FR-TASK-03 | 创建**定时计划**：按日/周/月/年及自定义间隔重复 | V1 | 支持「每 N 天」「每周一三五」「每月 15 号」「每月最后一个周五」「每年 5 月 20 日」 |
| FR-TASK-04 | 重复任务支持结束条件：永不结束 / 重复 N 次 / 到某日期止 | V1 | 三种条件均能正确截断展开序列 |
| FR-TASK-05 | 重复任务的**单次例外**：跳过某一次、或只改某一次的时间/标题 | V1 | 修改单次不影响其余次；跳过的次数不出现在任何视图 |
| FR-TASK-06 | 重复任务支持「本次及以后」批量修改 | V1 | 原规则在分割点截断，新规则从分割点起生效，历史记录保持不变 |
| FR-TASK-07 | 阶段事项与定时计划**可组合**（重复发生的多阶段事项） | V1 | 每个发生实例拥有独立的阶段完成状态 |
| FR-TASK-08 | 任务完成 / 取消完成 / 跳过 / 归档 / 删除（软删除） | V1 | 删除进回收站，30 天内可恢复；见 [任务生命周期](../02-domain/task-lifecycle.md) |
| FR-TASK-09 | 子任务清单（checklist）作为轻量拆分手段，区别于阶段 | ~~V1~~ **V2** | checklist 项不参与甘特/时间轴排布，只在详情页显示。**2026-09-10 用户收起了入口**（「把清单隐藏了，目前不需要这个」）—— 命令、表、DAO、导出都在，编辑器**既不显示也不读写**它。挪到 V2 而不是写进追溯豁免表：它的验收原话是「只在详情页显示」，而现在没有任何地方显示它，留在 V1 等于替一条界面上够不着的功能盖「已交付」的章 |

### 1.1 新建时的五种形态

加号点开是一个五选一的面板。**这五项不是五种任务类型** —— 它们是
`kind` × 重复 × 有没有日期的组合，落库仍然只有 `single` / `staged` 两种 `kind`
（见 `TaskShape`）：

| 面板上的选项 | 阶段 | 重复 | 时间 |
|---|---|---|---|
| 单事项 | ✘ | ✘ | **必填**开始与结束 |
| 阶段事项 | ✔ 至少 2 个 | ✘ | **由阶段推出**，见下 |
| 重复单事项 | ✘ | ✔ | 同单事项，另加重复设置 |
| 重复阶段事项 | ✔ 至少 2 个 | ✔ | 同阶段事项，另加重复设置 |
| 临时事项 | ✘ | ✘ | **不填**，进「无日期」那一组 |

### 新建/编辑表单按形态裁剪（用户 2026-09-10 定）

> 既然新建任务都用 5 个子项了，其对应的新建/编辑则隐藏无关设置项。

面板上已经选过「是哪一样」，表单再把五样的全部控件都摆出来，那次选择就
白选了。更糟的是**填了没用**：阶段事项的起止由阶段推出，日期栏里填什么
都会被下一次推导盖掉，而这个项目一直在防的正是「点了没反应」。

| 区 | 单事项 | 阶段事项 | 重复单事项 | 重复阶段事项 | 临时事项 |
|---|---|---|---|---|---|
| 全天 / 起止 | ✔ 必填 | **✘ 推出来的** | ✔ 必填 | **✘ 推出来的** | ✘ |
| 重复 | ✘ | ✘ | ✔ | ✔ | ✘ |
| 阶段 | ✘ | ✔ 每个的时间必填 | ✘ | ✔ 每个的时间必填 | ✘ |
| 提醒 | ✔ | ✔ | ✔ | ✔ | **✘ 没日期就不会响** |
| 标题 / 备注 / 分类 / 优先级 | ✔ | ✔ | ✔ | ✔ | ✔ |
| 清单 | ✘ | ✘ | ✘ | ✘ | ✘ |

#### 时间那一区长什么样（用户 2026-09-10 定）

> 1. 取消有结束时间这个选项，固定必须得有
> 2. 全天的开关往上点，启用下只用选个日期（进来默认就是启用全天、日期今天）。
>    禁用下有开始时间和结束时间，都是直接一轮选择日期+时间而非分成两步

| 全天 | 表单上有什么 | 语义 |
|---|---|---|
| 开（**默认**） | 一个日期栏 | 就是那一天：`endDate == planDate`，没有时刻 |
| 关 | 「开始」「结束」两颗按钮，各自**一次选完日期+时刻** | 起止四个值全必填 |

三处随之消失：**「有结束时间」那个开关**（结束现在必填，一个只能开着的
开关只是一次多余的点击）、**分成两步的日期栏与时刻栏**、以及**清空日期
那个叉**（日期必填，一个清完就再也存不下去的按钮不是选项，是陷阱）。

一轮是**原子**的：选完日期再取消时刻，改动整体作废。另一种做法是
「日期先落下」—— 那会让「点错了，算了」留下一个用户没打算要的日期，
而这一栏上没有撤销。

**代价，写明**：全天任务因此**只能是一天**。「出差 9/10–9/12 全天」
这种跨天的全天任务表达不了，要跨天就得关掉全天、填四个值。
用户 2026-09-10 明确要的就是这个形状。

#### 必填项：一个判据，两处读法

`TaskDraft.blockedReason` 是**唯一**的判据，`canSave` 只是把它读成布尔
（`canSave => 标题非空 && blockedReason == null`）。

一度是两张各自维护的清单，然后就分叉了：红字说「要先选结束日期」，
保存键同时亮着，按下去真的存了一条没有结束时间的单事项 ——
用户 2026-09-10 报的正是这条（「时间四件你没有检查必填」）。
两张清单不是「其中一张写漏了」，是**结构上必然会分叉**。

按形态必填的东西：

| 形态 | 缺什么就不能存 |
|---|---|
| 单事项 / 重复单事项 | 开始日期、结束日期；非全天时还要开始与结束时刻 |
| 阶段事项 / 重复阶段事项 | 至少两个阶段，**且每个阶段都要有时间** |
| 临时事项 | 只要标题 —— 这是它的定义 |

**校验对编辑同样生效**（2026-09-10 改）。原来只卡新建，理由是
「别拿新规矩去堵旧数据」—— 而这个 App 还没发版，库里根本没有旧数据，
那条豁免保护的是一个空集合，代价却是编辑路径上校验全失效。

守卫在 `editor_required_fields_test`：先守结构（两者不可能各说各话），
再按形态逐条守内容。顺序是有意的 —— 结构那条在，内容漏一条只会漏在一处。

**阶段事项的起止 = 阶段里最早的开始 → 最晚的结束。** 不是「第一个阶段的
开始 → 最后一个阶段的结束」：阶段可以交叠、也可以乱序。推导同时把偏移
重新表达成「相对最早那个阶段」，于是最早那个的偏移恒为 0
（`derived_span.dart`，判断全在那儿，`derived_span_test` 逐条验）。

**阶段事项没有「全天」。** 阶段时间一律带时刻 —— 任务层面不再有「全天」
这个概念，它的跨度是推出来的。（另一条路是让阶段也能设全天，那要动
`occurrenceKey` 的形态，用户 2026-09-10 选了不做。）

**两条逃生口，都是刻意的**：

1. **编辑已有任务时，时间那几个控件回来。** 形态是从当前字段反推的
   （`TaskShape.of` 只看它现在是什么样）—— 藏起来的话「给这条临时事项
   加上时间」那条路就断了：想加时间要先变成单事项，而想变成单事项
   又得先加时间。
2. **编辑一条 `kind=staged` 却一个阶段都没有的旧数据时也回来。**
   那时没有东西能推，藏起来等于把它锁死。（只在**编辑**时 ——
   新建的阶段事项本来就从零个阶段起步。）

矩阵由 `editor_shape_fields_test` 逐格盯着，那份用例里的表就是这张表。

#### 老数据会在什么条件下被改形态

**一条 `isAllDay = true` 的旧阶段事项，在推导跑起来的那一刻会被置为
非全天。** 必须一起改：推出来的起止带时刻，而「全天却带 startMinute」
会被 `checkInvariants` 当场拒 —— 用户看到的只是保存时炸一下。

但要写明白的是**它发生的时机**：那是一次有意的迁移，而它触发于
**用户点开编辑器并让阶段时间变动**的时候，不是他做了某个选择的时候。
这条写在这儿，是因为「什么时候老数据会被改」属于用户该能查到的事。

> **FR-TASK-01 的验收标准改过一次。** 原文是「仅填标题即可保存」，
> 而新的形态面板要求单事项必须有起止。用户的裁决是「以本次为准，改验收」——
> 「仅填标题」那一档由**临时事项**承接，所以那个需求没有丢，
> 只是换了个入口：它从「所有新建任务的下限」变成「五个选项里的一个」。
>
> 阶段事项的起止**填在阶段级还是任务级**（「事项以阶段的最早/最晚时间作为开始/结束」）
> 用户明确挂起：「待定，先做其他我再想想」。当前实现是任务级必填，与单事项一致。

### 4.1 V1 的提醒界面只给「提前多久」

领域层的 `ReminderKind` 有三种：相对开始、相对结束、绝对时刻。三种都实现了、
排期都算得对、导入与将来的 Agent 都构造得出来（FR-AI-01）。
**但编辑器里只给相对开始那一档。**

另外两档各要多一组控件（选基准点、选绝对日期与时刻），而「提前多久」
覆盖了绝大多数场景。**这是界面上的取舍，不是能力上的缺失** ——
所以编辑器读草稿时会把别的 kind 原样留在库里，不读进来：
读进来会在保存时被整表替换掉，那等于用户点开编辑页看一眼，
导入进来的绝对提醒就没了。

要补的话是纯界面工作，领域层与排期一行都不用改。

## 7. 非功能需求 NFR

### 7.1 性能 NFR-PERF

| 编号 | 需求 | 阈值 | 怎么测 |
|---|---|---|---|
| NFR-PERF-01 | 冷启动到首屏可交互 | ≤ 1.5s（中端机） | 集成测试打点 + 手工基准 |
| NFR-PERF-02 | 1000 任务下视图滚动 | 掉帧率 < 1% | **V1 不验**，见 §7.1.1 |
| NFR-PERF-03 | 单次任务写入到 UI 更新 | ≤ 100ms | 集成测试计时断言 |
| NFR-PERF-04 | 重复规则展开 1 年实例 | ≤ 50ms | 领域层基准测试，作为回归门禁 |

#### 7.1.1 NFR-PERF-02 在 V1 降级为**不验收**

用户 2026-09-09 明确决定。

**为什么。** 掉帧率只能在 profile 模式的真机上量 —— 模拟器的帧时间由
宿主机的调度决定，它给出的数字既可能好看得离谱，也可能因为宿主机在编译
而突然变差。**拿模拟器的采样当验收，比不测更糟**：它会给出一个看起来
通过了的数字。开发期没有可用的真机，所以这条要么等设备，要么降级；
用户选了降级。

**降级成什么。** 阈值本身留着（它仍然是设计目标，`view-specs` §4.4 那几条
防掉帧措施照做），但 V1 **不声称验过**。当前实际验的是它的一个上游代理：

| 真正的问题 | V1 验的 | 差在哪 |
|---|---|---|
| 滚动时每帧掉不掉 | 排布 / 展开的**单次耗时**（`view_layout_benchmark_test.dart`，1000 条任务） | 只覆盖 CPU 侧的布局计算，不含光栅化、不含真机的调度与热节流 |

代理绿了不等于这条需求满足了。**这一行就是为了让那句话写在纸上** ——
`check_traceability.py` 的豁免表里也记着同一件事（一度靠一句注释算作
有覆盖，而那个基准量的是排布耗时，不是掉帧）。

**什么时候补。** 拿到真机之后按原方案量（`flutter run --profile` +
timeline 采样）。在那之前，任何「性能没问题」的说法都只有代理作支撑。

### 7.2 可靠性 NFR-REL

### 7.4 可访问性与本地化 NFR-A11Y

| 编号 | 需求 |
|---|---|
| NFR-A11Y-01 | 正文文字对比度 ≥ 4.5:1（可爱清新的低饱和配色**必须**通过这条，不得为了好看牺牲可读） |
| NFR-A11Y-02 | 支持系统字号缩放至 200% 不破版。**注意应用内 `theme.fontScale`（≤1.4）与之相乘**，实际须验到 2.8 —— 见[设计系统 §3.4](../03-design/design-system.md#34-缩放是两层相乘golden-必须覆盖到实际最坏值) |

| NFR-A11Y-04 | 文案全部走本地化资源，首发中文，架构支持追加语言 |
| NFR-A11Y-05 | **已知偏离**：控件边界不满足 WCAG 1.4.11 的 3:1。中性色三个表面刻意设计得极为接近（对比低至 1.07:1），低反差是「可爱清新」观感的一部分。**代偿**：所有控件状态由文字 / 图标 / 填充多重承载，不依赖边界；文字与承载状态的图形仍分别满足 4.5:1 与 3:1。详见[无障碍声明](accessibility.md) §2 与[设计系统 §8.5](../03-design/design-system.md) |
