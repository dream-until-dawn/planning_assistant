# ADR-0005：计划时间存「墙钟 + IANA 时区」，不存 UTC 时间戳

**状态**：✅ 已采纳 · 2026-09-07

## 背景

日历/计划类应用最经典的一类 bug：用户设了「每天 07:00 起床」，出国后变成了半夜 3 点。
根源是把「用户心智中的时间」当成「绝对时刻」来存。

## 决策

区分三种时间，各有各的存储形态：

| 类型 | 存储 | 用于 |
|---|---|---|
| `Instant` | UTC 毫秒整数 | `createdAt`、`completedAt`、通知实际触发时刻 |
| `LocalWallTime` | `planDate`(TEXT) + `minuteOfDay`(INT) + `timeZoneId`(TEXT) | **所有计划时间** |
| `PlanDate` | TEXT `yyyy-MM-dd` | 全天任务 |

转换只能经过 `core/time/TimeZoneResolver` 一个入口。
业务代码中**禁止直接 `DateTime.now()`**，由架构守卫测试强制。

## 后果

**收益**

- 「每天 07:00」跨时区后仍是当地 07:00，符合用户预期。
- 与 iCalendar 的 `DTSTART;TZID=` 语义一致，导入导出与云端互通自然。
- 服务端拿到墙钟 + 时区就能自己算绝对时刻，不依赖客户端（云端发邮件的前提）。
- `rrule` 包本身是时区无关的（要求 `isUtc=true` 但按纯墙钟处理），**恰好**匹配这个模型 ——
  时区换算的责任干净地落在 `core/time`，展开逻辑不碰时区。

**代价**

- 多存一列 `timeZoneId`。
- 排序跨时区任务时需要先转成 `Instant`，多一步。
- 夏令时的两个坑必须显式处理（跳过的小时、重复的小时），且必须写测试 ——
  即使中国大陆当前无夏令时。**「国内用不到」正是永远绿测试的温床。**

## 被否决的方案

| 方案 | 为什么不选 |
|---|---|
| 全部存 UTC 时间戳 | 最简单，也最错。跨时区后所有计划时间集体漂移 |
| 全部存本地时间字符串，不记时区 | 无法算出绝对触发时刻，通知无从排期；服务端更是无解 |
| 存 UTC + 另存一个「显示用」的本地时间 | 两份数据必然不同步，是更糟的版本 |

## 什么情况下该推翻

- 基本不该推翻。这是日历类应用的既定正确做法。
- 唯一可能的调整：若某类任务确实需要「绝对时刻」语义（例如跨时区会议的参与者视角），
  则为该类任务**新增**一种时间模式，而不是改掉现有模式。
