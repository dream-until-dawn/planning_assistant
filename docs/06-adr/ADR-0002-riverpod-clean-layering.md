# ADR-0002：Riverpod 3 + 分层 Clean 架构

**状态**：✅ 已采纳 · 2026-09-07

## 背景

四个视图共享同一份任务数据与筛选状态；数据以响应式流从 SQLite 流向 UI；
后续要接入云同步与 AI Agent，两者都需要一个稳定的「写入入口」。

## 决策

1. **状态管理与依赖注入统一用 Riverpod 3**（`flutter_riverpod 3.4.3` + `riverpod_generator 4.0.9`）。
2. **分四层**：Presentation → Application → Domain ← Data，依赖方向单一，由守卫测试强制。
3. **所有写操作收敛为 `TaskCommand`**，经统一的 `CommandDispatcher` 执行。

## 后果

**收益**

- Provider 的 override 机制让测试中替换依赖极其廉价，不需要 mock 框架也能隔离。
- 代码生成消除了手写 Provider 的样板与类型错误。
- 领域层零 Flutter 依赖 → 领域测试跑在纯 Dart VM，秒级反馈。
- 单一写入口一次性解决：撤销重做、变更日志、云端下发变更、Agent 接入 —— 这四件事共用同一条管道。

**代价**

- 需要跑 `build_runner`，改注解后忘记重新生成会报奇怪的错（CI 会抓）。
- 分层带来的间接层对小改动是额外成本（加一个字段要动实体、mapper、DTO、表）。
- 命令管道比「UI 直接调 Repository」多一层，短期看是额外工作量。

**为什么仍然值得**：这些代价在 V1 就要付，但收益在 V2/V3/V4 才完全兑现。
如果 V1 图快省掉命令管道，V4 接 Agent 时要重做全部写路径 —— 那时的代价是现在的十倍。

## 被否决的方案

| 方案 | 为什么不选 |
|---|---|
| BLoC 8 | 事件溯源特性好，团队规范性强；但样板代码量约为 Riverpod 的两倍，单人开发下拖慢迭代 |
| Provider + MVVM | 上手最快，但跨视图状态编排与异步缓存要手写，接同步引擎/Agent 时容易失控 |
| 不分层，直接 Widget 调 DB | 短期最快。但四视图共享状态、云同步、Agent 三个需求任一出现都会崩塌 |
| 全局单例 / service locator | 与可测试性目标冲突，测试中难以隔离 |

## 什么情况下该推翻

- 若 Riverpod 3 的代码生成在后续版本出现无法接受的兼容性断裂。
- 若实践中发现「命令管道」在 V1 内始终没有第二个调用方，且明显拖慢开发 ——
  但推翻前必须先确认 V3/V4 的计划是否已取消。
