# ADR-0006：V1 就带同步信封与 outbox

**状态**：✅ 已采纳 · 2026-09-07

## 背景

云同步是 V3 的事。诱惑是「V1 先不管，等要做同步了再加字段」。

## 决策

**V1 的每张可同步表都带完整同步信封**（`createdAt`/`updatedAt`/`deletedAt`/`revision`/
`lastWriterId`/`remoteVersion`），**且每次写操作在同一事务内写 `change_log`（outbox）**。
删除一律用墓碑，不物理删除。

## 后果

**收益**

- V3 做同步时不需要数据迁移，也不需要面对「老数据没有这些字段该怎么办」。
- 墓碑从第一天就有：否则 V3 时无法知道「历史上删过什么」，已删数据会在同步时复活。
- outbox 在 V1 内部就有价值：**回放一致性测试**（清库 → 按 seq 回放 → 断言状态等价）
  是发现「有写操作绕过了命令管道」的最有效手段。这个测试在 V1 就能捉到真实缺陷。
- 导出格式从 V1 起就是最终形态，V2/V3 加功能不用升导出格式版本。

**代价**

- 每张表多 6 列，每次写入多一次 outbox 插入。
- 所有查询必须记得带 `deletedAt IS NULL` —— 用 DAO 基类统一处理，并由守卫测试检查。
- 回收站与物理清理逻辑要在 V1 就写。

**成本对比**：现在带上的成本是「多写几列 + 一个基类」；后补的成本是
「数据迁移 + 无法恢复的历史删除信息 + 已发布用户的数据要特殊处理」。差了一个数量级。

## 被否决的方案

| 方案 | 为什么不选 |
|---|---|
| V3 再加字段 | `deletedAt` 无法追溯 —— V1 期间物理删除的记录，V3 时无从知晓，会在同步时复活 |
| 只加 `updatedAt` | 不足以做冲突检测（无法区分「我改过」和「别人改过」） |
| 用自增整数主键 | 多端合并时主键必然冲突。所以主键用 UUID v7 |

## 什么情况下该推翻

- 若 V3 的云同步计划被明确取消，且导出/导入也不再需要墓碑 ——
  那时可以考虑简化，但收益很小（省几列），不值得改动风险。
- 实践中更可能的调整是**增强**而非推翻：V3 需要引入设备注册表，
  才能安全判断「墓碑何时可以物理清理」（见[云同步预研 §3.3](../04-platform/future-sync.md) 的已知缺口）。
