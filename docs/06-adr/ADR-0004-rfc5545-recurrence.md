# ADR-0004：重复规则用 RFC 5545 RRULE，实例不预存

**状态**：✅ 已采纳 · 2026-09-07

## 背景

需求要「定时计划/定时事项（如每月每周每日等）」，且后续云端要能读取任务并发邮件 ——
这意味着**服务端必须能独立算出「下一次什么时候发生」**。

## 决策

1. 重复规则存 **RFC 5545 的 `RRULE:` 字符串**，用 `rrule 0.2.18` 包解析与展开。
2. **不预存发生实例**。DB 只存规则 + 例外（`occurrence_overrides`），实例在查询时按可见时间窗展开。
3. 单次例外用 `occurrenceKey = 原始发生时刻` 标识，语义对齐 iCalendar 的 `RECURRENCE-ID`。

## 后果

**收益**

- 「每天，永不结束」不需要无限行。
- 服务端用任何语言的成熟 RRULE 库即可解析，**不需要移植客户端逻辑** —— 这是云端发邮件能成立的前提。
- 将来导入导出 `.ics` 不失真，可与系统日历互通。

> ⚠️ 上面两条收益**不是白拿的**，它们依赖「导出的 RRULE 串真的合规」。实测发现两个陷阱：
> `rrule` 的 `toString()` 默认丢掉 `UNTIL` 的 `Z`（产出不合规的浮动时间串），
> 且 `UNTIL` 在包内是朴素比较、不做时区换算。
> 两者都会**静默**破坏这两条收益，且本地测试发现不了。
> 因此本 ADR 的成立**以下述两条约束被强制执行为前提**：
> [重复引擎 §2.2](../02-domain/recurrence-engine.md#22-until-的时间域必须显式换算)（UNTIL 显式换算）与
> [§2.3](../02-domain/recurrence-engine.md#23-编码-rrule-必须显式开启-istimeutc强制)（编码强制 `isTimeUtc: true`）。

**代价**

- 每次查询都要展开，需要缓存与窗口化才能满足性能要求（见[重复引擎 §5](../02-domain/recurrence-engine.md)）。
- 例外处理有反直觉的坑：把窗口外的一次挪进窗口时，必须额外查询才能不丢失
  （见[重复引擎 §3.1](../02-domain/recurrence-engine.md)）。
- **`UNTIL` 横跨两个时间域**：RFC 要求真 UTC，而展开在墙钟域进行，两者之间必须显式换算。
  这是本方案最尖锐的一处代价，处理不当会静默多一次或少一次（§2.2 有 UTC+14 / UTC-11 的具体反例）。
- RFC 语义与用户直觉存在偏差，必须在 UI 层做提示 —— 见下。

**已实测的语义偏差**：`FREQ=MONTHLY;BYMONTHDAY=31` 在没有 31 号的月份**直接跳过**
（2026 年展开为 `01-31, 03-31, 05-31, 07-31`，2/4/6 月缺席），而多数用户以为是「顺延到月末」。
对策：UI 在用户选「每月 31 号」时明确提示，并提供「每月最后一天」（`BYMONTHDAY=-1`）作为替代。
**这是先实测后写文档的直接收益 —— 凭直觉写下的期望值会是错的。**

## 被否决的方案

| 方案 | 为什么不选 |
|---|---|
| 自定义重复规则格式 | 短期更贴合 UI，但服务端要实现一套私有解析器，`.ics` 互通也没了。为省一点前期工作，透支了云端能力 |
| 预生成所有实例存表 | 查询最简单，但「永不结束」无解；改规则要重算全部历史；同步时数据量爆炸 |
| 预生成未来 N 年实例 | 是上一条的妥协版，仍有「N 年后怎么办」和「改规则要重算」的问题，且同步数据量大 |
| 自己实现 RRULE 展开 | RFC 5545 的边界情况极多（`BYSETPOS`、负序号、闰年、月末），重写必然出错。已有可用的 Dart 实现 |

## 什么情况下该推翻

- 若性能实测表明惰性展开无法满足 NFR-PERF-04（1 年 ≤ 50ms），且缓存优化已用尽 ——
  那时可考虑「热窗口预物化 + 冷窗口惰性展开」的混合方案，**但存储格式仍应保持 RRULE**。
- 若 `rrule` 包停止维护且出现无法绕过的正确性缺陷 —— 换库，不换格式。
