# 路线图与里程碑

> 原则：**每个里程碑都有可验收的产出**，且验收标准是可自动化检验的，不是「感觉差不多了」。
> 没通过验收的里程碑不进入下一个 —— 尤其 M1，它承载了所有「为后续留口」的兑现。

## 总览

| 版本 | 里程碑 | 产出 |
|---|---|---|
| **V1** | M0 工程基建 | 可构建的空壳 + CI + 规范落地 |
| | M1 领域内核 | 模型 + DB + 重复引擎 + 命令管道（**无 UI**） |
| | M2 基础 UI | 设计系统 + 列表视图 + 任务增删改 |
| | M3 四视图 | 时间轴 + 日历 + 竖向甘特 |
| | M4 配置与提醒 | 配置中心 + 本地通知 |
| | M5 打磨出包 | 性能、无障碍、导入导出、签名发布 |
| **V2** | 桌面小组件与通知栏 | |
| **V3** | 云同步 / 恢复 / 邮件 | |
| **V4** | 语音与 AI Agent | |

## M0 · 工程基建

**产出**：一个能构建出 APK 的 Flutter 工程骨架，CI 跑通，规范落地。

| 任务 |
|---|
| `flutter create` 骨架，按[模块与目录规范](../01-architecture/module-map.md)建目录 |
| 配置 Gradle 阿里云镜像、desugaring、compileSdk、minSdk |
| `analysis_options.yaml` + 自定义 lint |
| CI：analyze / codegen 校验 / test / guard / build |
| 架构守卫测试骨架（此时应该是**通过**的，因为还没代码可违规） |
| 完成[环境探针结论 §6 的 M0 检查表](../05-engineering/environment-notes.md)全部条目 |

**验收**

- [ ] `flutter build apk --debug` 成功
- [ ] CI 全绿
- [ ] `compileSdk` 决策已定（能否移除 `permission_handler` 降回 36）
- [ ] `uuid` 的 v7 API 已实测确认（或已自实现）
- [ ] 重复引擎探针 P-3/P-4/P-5 完成，结论写入文档
- [ ] 断网启动无网络请求（字体已打包）
- [ ] **故意写一个违反分层的 import，确认守卫测试变红** ← 验证守卫真的有效
- [ ] 同样地：故意留一个 `assert(` 在 `lib/domain/`，确认 lint 守卫变红
- [ ] `python tool/check_doc_links.py --self-test` 进 CI 且自检通过
- [ ] **以上每一条都把「变红的输出」贴进 M0 记录**，而不是只写「已验证」

> 最后几条是本项目的规矩：**任何守卫机制建立时，必须当场证明它能失败**，
> 否则它就是又一个「永远绿的测试」。这条规矩适用于守卫、lint、校验脚本、CI 门禁
> —— 凡是「报绿就放行」的东西都适用。详见[测试策略 §1.4](../05-engineering/testing-strategy.md)。
>
> 文档链接校验器已按此完成两步验证（自检 + 对真实仓库注入坏链），失败输出留档在 §1.4。

### M1 遗留：10 条必测用例依赖尚未实现的功能

**不勾选，也不下调要求。** 这些用例对应的功能本就排在后面的里程碑，
现在勾上等于把「验收」变成走过场。逐条记下欠账与到期时间：

| 用例 | 依赖的功能 | 何时补 |
|---|---|---|
| R-26 | 导入 `.ics`（含 `EXDATE` → override） | M5 数据迁移 |
| R-27 | 全天 ⇄ 定时切换时 `occurrenceKey` 迁移 | M3 编辑器支持改任务形态时 |
| R-30 / R-31 / R-32 | 「本次及以后」分裂（FR-TASK-06） | M3 |
| R-43 | 跨时区后重排通知 | M4 提醒 |
| R-50 / R-51 / R-52 | 重复阶段事项的每次发生状态 | M3 阶段编辑 |

已通过的 30 条中，R-40/R-41/R-42（时区三条）是这次补的 ——
补的过程中发现引擎**根本没做 DST 解析**：春季跳表日会产出一个当天
不存在的墙钟（`America/New_York` 的 02:30），日历会显示一个不存在的时刻，
而排通知时又会被换算到别处，两边对不上。已按 §4.1 修正并在 `Occurrence`
上加了 `dstAdjusted` 标记。去掉该解析后 2 条用例稳定变红。

## M3 · 四视图

| 任务 | |
|---|---|
| 共享层：窗口展开（`expandInWindow`）+ 重叠排布（`layoutOverlaps`） | ✅ |
| 时间轴视图（含重叠布局、「随时」区、当前时刻线、「+N」） | ✅ |
| 日历视图（月/周） | ✅ |
| 竖向甘特视图（`CustomPainter` + 布局算法） | ✅ |
| 视图间状态一致性 | ✅ |

顺带补上的两处（都是接时间轴时才露出来的）：

- 重复任务的每一次**从来没有结束时刻** —— `durationMinutes` 声明了、
  引擎读它、引擎的测试也测了，但没有任何地方**写**它
  （[测试策略 §1.9](../05-engineering/testing-strategy.md#19-两侧都测到了中间那根线没人接)）；
- 展开按开始日期筛，于是「昨晚 22:00 干到今早 6:00」在今天的时间轴上
  是空的。改成按覆盖区间收。

**验收**

- [x] [甘特布局必测用例](../03-design/view-specs.md#45-布局算法必测用例) G-01..G-07 通过
- [x] [视图切换一致性](../03-design/view-specs.md#5-视图切换的一致性fr-view-0506)四条集成测试通过
- [ ] 1000 条任务下四视图滚动掉帧率 < 1%（profile 模式实测）—— **只做了一半**：
      布局计算这一半有基准（`test/application/view_layout_benchmark_test.dart`，
      含一条挡 O(n²) 的增长曲线用例）；**掉帧率本身还没在真机 profile 模式量过**。
      模拟器的帧时间不代表真机，量了也说明不了问题，所以不拿它充数。
- [x] 集成测试 J-02、J-03 通过

## 里程碑之间的硬规矩

1. 上一个里程碑的验收未全部通过，不开始下一个。
2. 每个里程碑结束时更新受影响的文档（不是「有空再补」）。
3. 每个里程碑结束时打 tag：`v0.1.0-m1` 这样。
4. M1 与 M5 各做一次变异演练，报告入库。
