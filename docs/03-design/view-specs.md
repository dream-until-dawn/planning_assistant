# 四视图规格

> 对应需求 FR-VIEW-01..07。
> 四个视图**共享同一份数据源与筛选状态**（`visibleOccurrencesProvider`），各自只负责布局与交互。
> 这是 FR-VIEW-05/06 能成立的架构前提，见[架构总览](../01-architecture/overview.md) §3。

## 0. 共享层

### 0.1 共享状态

```dart
ViewSharedState {
  DateTime focusedDate;        // 当前聚焦日期，视图切换时保持
  FilterSpec filter;           // 分类/标签/优先级/状态/关键词，视图切换时保持
  String? selectedOccurrenceId;
  TimeGranularity granularity; // 日/周/月，甘特与日历共用
}
```

### 0.2 共享数据源

```dart
// 输入: 可见时间窗 + 筛选  →  输出: 已展开、已应用例外、已排序的实例
Stream<List<Occurrence>> visibleOccurrences(DateRange window, FilterSpec filter)
```

每个视图声明自己需要的 `window`（时间轴要 1 天，日历月视图要 1 个月 + 前后补齐），
其余完全一致。**禁止**任何视图自己查库。

#### 0.2.1 列表的窗口，以及窗口装不下的两类东西

实现时出参不是 `Occurrence` 而是 `TaskOccurrence`（`(任务, 可选的某一次)`），
因为有两类东西 `Occurrence` 表达不了，而它们都不能从列表里消失：

| | `Occurrence` 能表达吗 | 为什么不能丢 |
|---|---|---|
| **没有日期**的任务 | ✘ `start` 是必填墙钟 | §2.1 专门有「无日期」这一组；FR-TASK-01 说仅填标题即可保存 |
| 窗口**之外**的一次性任务 | ✘ 窗口外不产出 | 「明年那件事」从列表里消失，会让人以为它丢了 |

于是展开的规则是：

- 无日期 → 一行，`occurrence` 为 null；
- 不重复 → 一行，**不看窗口**（它只有一次，不存在展不完的问题）；
- 重复 → 见下。

#### 0.2.2 重复任务：逾期的全留，未来只留「下一次」

一度是「窗口内每次一行」。实测下来那不能用：一条「每天」在列表里就是
**六十一行**，逾期组还会往上堆 —— 那不是一份计划，是一份日历的转录。

| 那一次 | 显示吗 | 为什么 |
|---|---|---|
| 没做完，日期在今天之前 | **留着**（逾期组） | 漏交一次房租不该无声消失 |
| 没做完，今天或以后 | **只留最早的一条** | 那就是「下一次」 |
| 已完成，今天或以后 | 留着 | 刚勾掉的卡片不能立刻消失（[§8.1](design-system.md#81-任务卡片最重要的组件)），要给撤销留时间 |
| 已完成，且已是过去 | 不留 | 否则天天堆划掉的行 |
| 已跳过 | 不留 | FR-TASK-05 验收：「不出现在任何视图」 |

于是勾掉今天那次之后，**下一次当场顶上来**，而刚勾的那张划掉的卡片
还在原位可以撤销。跳过同理。

最后两栏被折叠掉的那些，**只有在筛选条里显式勾「已完成」/「已跳过」
时才回来**（`expandForList` 的 `includeCompleted` / `includeSkipped`）。
这是它们唯一的入口 —— 没有这条路的话，做完或跳过的那些次就再也
找不回来，与「到某天为止」那条死路是同一种毛病。

#### 0.2.2.1 时间轴与日历用的是另一个函数

`expandInWindow`：**窗口内的全部发生，一次不落，不做任何折叠。**
它们问的是「这段时间里都发生什么」，答案由日期决定，不掺取舍。

合成一个带开关的函数的话，「日历为什么少了几天」会变成一道
要读策略分支才答得上的题。

两条与列表不同的规矩：

- **没有日期的任务不进来** —— 它不落在任何一天上（列表另有「无日期」组）；
- **按覆盖区间收，不按开始日期** —— 「9/1 到 9/30 的项目」在 9/15
  那天必须在，昨晚 22:00 的值夜在今天早上也必须在。

重复的跨天任务另有一道手续：引擎是按**开始日期**筛的
（`window.contains(occ.start.date)`），所以展开时要往前多要几天，
多要的天数按**任务自己的时长**算，上限 62 天
（`_maxSpanDays`，性质同 `lookaheadDays`：刻意的上界，不是遗漏）。

这个上界由 `expand_in_window_test.dart` 的**两条边界用例**夹住：
跨 62 天的在、跨 63 天的缺席。少了后一条，把上限改成 400 全绿 ——
而那会让每条重复规则都多展开三百多天。

#### 0.2.3 三个窗口常量（`ListHorizon`）

| 常量 | 值 | 决定什么 |
|---|---|---|
| `pastDays` | 14 | 逾期最多回溯多久。再长的话，搁置三个月的每日任务会堆出九十行 |
| `futureDays` | 60 | 往前找「下一次」时多远以内算便宜。它**不再决定行数** |
| `lookaheadDays` | 732 | 兜底。「每年 5 月 20 日」在九月时下一次在八个月后，只看 60 天的话**整条任务从列表里消失** |

比 `lookaheadDays` 还稀疏的规则（每三年）不显示「下一次」，只显示逾期的
那些 —— 这是刻意的上界，不是遗漏。

> 「每天」这类规则是无限的，而 §2.1 的「更远」字面上没有尽头 ——
> 两者不可兼得。折叠成「下一次」之后，「更远」组里装的就只有
> 一次性任务与各条规则的下一次了。

### 0.3 共享交互

| 交互 | 所有视图一致 |
|---|---|
| 点击实例 | 打开详情底部弹层 |
| 长按空白 | 在该时间点快速新增（FR-VIEW-07） |
| 完成钮 | 就地完成 + 撤销 Snackbar |
| 顶部筛选条 | 同一个组件，同一份状态 |
| 悬浮新增按钮 | 常驻右下，带当前上下文 |

```

│  9月8日 周一            [今天] [筛选]     │ ← 顶栏
├─────────────────────────────────────────┤
│  随时                                    │ ← 无时间任务区（可折叠）
│   ○ 买牛奶            ○ 回邮件            │
├─────────────────────────────────────────┤
│ 08:00 ─────────────────────────────────  │
│       ┌──────────────┐                   │

│       └──────────────┘                   │
```

### 1.2 关键规则

| 规则 | 说明 |
|---|---|
| 刻度粒度 | 配置项 `view.timelineTickMinutes`，默认 60，可选 15/30/60 |

| 当前时刻线 | 仅在「今天」显示，每分钟更新 |
| 首次进入定位 | 滚动到当前时刻前 1 小时；非今天则滚到当日首个任务 |
| 跨天任务 | 在当日只显示当日覆盖的时段，块边缘用渐隐表示「延续」 |

### 1.3 空态

插画 + 「今天还没有安排，要加点什么吗？」+ 新增按钮。

## 2. 列表视图 TaskListView（FR-VIEW-02）

### 2.1 分组维度（可切换，配置项 `view.listGroupBy`）

| 维度 | 分组顺序 |
|---|---|
| 按日期（默认） | 逾期 → 今天 → 明天 → 本周 → 更远 → 无日期 |
| 按分类 | 分类自定义 `orderIndex` |
| 按优先级 | 紧急 → 高 → 普通 → 低 → 无 |
| 按状态 | 进行中 → 待办 → 已完成 |

### 2.2 组内排序（配置项 `view.listSortBy`）

时间升序（默认）/ 优先级降序 / 创建时间 / 手动（`sortOrder`，支持拖拽）

### 2.3 筛选

分类（多选）、标签（多选）、优先级（多选）、状态（多选）、关键词、日期范围。
**条件可叠加**，顶部以 Chip 形式展示已生效条件，可单个清除。

### 2.4 交互

| 手势 | 默认动作（可在配置中改，`behavior.swipeLeft/Right`） |
|---|---|
| 右滑 | 完成 |
| 左滑 | 推迟到明天 |
| 长按 | 进入多选模式，批量操作（**M3**） |

滑动的可选动作：`complete` / `postpone` / `delete` / `none`。

`delete` 一度**不在里面**，理由是「滑一下就把整条重复任务删掉，
在误触时代价太大，而当时唯一的退路是一条 Snackbar —— 划走了就找不回来」。
回收站做出来（FR-TASK-08）之后这个理由消失了：删除是软删除，
进回收站，随时能恢复。所以补上。

> 这段留着不是为了记「当时没做」，是为了记**判据**：
> 一个动作能不能放进滑动手势，看的是「误触之后有没有回头路」。

滑动是最容易误触的手势（列表本来就要上下滚），所以**每次滑动都配一条
撤销 Snackbar**（§0.3）。撤销闭包由动作本身给出，不是界面层再算一遍：
「推迟」的撤销要回到**原来那天**，而那个值只有动作知道；
「完成」的撤销要回到**切换之前**的状态，再调一次切换等于又切回去。

推迟的粒度目前固定是**一天**。`behavior.postponeMinutes` 没进注册表 ——
按分钟推迟还没有消费者，而没有消费者的声明就是一个改了没反应的开关。

「逾期」分组默认折叠并显示计数 —— 展开是用户的主动选择，避免一打开就被一堆红字压住。

## 3. 日历视图 CalendarView（FR-VIEW-03）

### 3.1 结构

上半月历格子 + 下半选中日列表，比例可拖拽（记住用户选择）。

| 模式 | 说明 |
|---|---|
| 月视图（默认） | 6 行格子；格子内显示最多 3 个色点 + 「+N」 |
| 周视图 | 一行 7 格，格子内显示任务标题缩略 |

### 3.2 关键规则

- 一周起始日来自配置项 `view.firstDayOfWeek`，默认周一。
- 今天：主色描边圆；选中：主色实心圆 + `text.onBrand`。
- 色点颜色取分类色；**同时**在下方列表显示分类名（颜色非唯一载体）。
- 全天/跨天任务在格子顶部以横条贯穿，连续多日不断开。
- 左右滑动切月，带惯性；`reduceMotion` 时改为无动画直接切换。

### 3.3 基础组件：**自己搭，不用 `table_calendar`**（决定已变更）

原定用 `table_calendar 3.2.1` 当骨架，「只为省掉日期网格与滑动分页的边界处理」。
做到这一步时去读了它的源码，那个前提不成立：

**它的 builder 全是按格子调的** —— `FocusedDayBuilder`、`DayBuilder`、`MarkerBuilder`
都只拿得到一个 `day`。连 `rangeHighlightBuilder` 也是（签名是 `(context, day, isWithinRange)`，
在每格自己的 `LayoutBuilder` 里调用）。它自己那条跨天高亮，就是**每格画一条到边的横条
拼出来的**，两端各留 50% 边距。

而 §3.2 要的是「全天/跨天任务以横条贯穿，**连续多日不断开**」，且同一行里可能有多条
不同层的横条。在按格子的模型下，这要么把 `rangeHighlightBuilder` 挪作他用去画一整摞层，
要么每格自己拼——两条路都是在跟这个库的模型对着干，而拼接处的半像素缝没有测试盯得住。

自己搭之后：**一周就是一个 widget**，横条是 `Stack` + `Positioned(left: i*w, width: n*w)`，
不存在缝。而它本来要省的两件事：日期网格是 `month_grid.dart`（纯函数，带 16 条用例），
滑动分页是一个 `PageView`。

依赖已从 `pubspec.yaml` 移除。

> 这条记在这里而不是悄悄改掉：原来的选择是有理由的（省边界处理），
> 变更的理由也很具体（那个库的模型与这条硬需求冲突）。
> 只留结论不留过程的话，下一个人会重新提议用 `table_calendar`。

## 4. 竖向甘特视图 GanttView（FR-VIEW-04）

这是最独特也最难的视图，单独展开。

### 4.1 为什么是竖向

手机是竖屏长条。横向甘特在手机上只能看到 2–3 天，失去「纵览」意义。
**竖向**：时间从上往下流动（与阅读方向一致），泳道横向排列，一屏能看两周以上。

### 4.2 布局

```
        │ 学习    │ 工作    │ 生活    │   ← 泳道表头（吸顶）
────────┼─────────┼─────────┼─────────┤
 9/8 一 │ ┃阶段1  │ ┃周报   │         │
 9/9 二 │ ┃       │ ┗━━━   │ ┃健身   │
 9/10三 │ ┃       │         │         │
 9/11四 │ ┣阶段2  │ ┃方案   │ ┃健身   │   ← 阶段分段换色
 9/12五 │ ┃       │ ┃       │         │
 9/13六 │ ┗━━━   │ ┗━━━   │         │
────────┴─────────┴─────────┴─────────┘
   ↑ 时间轴（吸左）
```

### 4.3 关键规则

| 规则 | 说明 |
|---|---|
| 泳道维度 | 配置项 `view.ganttLaneBy`：按分类（默认）/ 按任务 / 按标签 |
| 时间粒度 | 日 / 周 / 月三档，双指缩放或顶部切换 |
| 阶段条 | 一个阶段事项画成**一根连续的条**，按阶段分段换色，段间有 2dp 缺口 |
| 进度 | 已完成的阶段段落填实，未完成为半透明 + 左边线（不是虚线边，见下） |
| 今日线 | 横贯所有泳道的水平线 |
| 重叠 | 同泳道同时段多任务时，泳道内再分列（最多 3 列，超出折叠） |
| 无日期任务 | 不出现在甘特图（甘特的本质是时间跨度） |
| **没排时间的阶段** | **不切段**，改画一条进度填充，见 §4.3.1 |
| 点击段落 | 直接定位到该阶段，可就地标完成 |

### 4.3.1 没排时间的阶段：给进度，不给编造出来的段

编辑器**默认不给阶段排时间** —— 用户加三个阶段、写个名字就存了。
那时把条按阶段数**均分**是很诱人的（三段各三分之一），但那是在编造数据：
它等于告诉用户「第一阶段在前三分之一结束」，而他从没这么说过。
与 §1.2「不替用户假设时长」是同一条原则。

所以分两种：

| 阶段有没有排时间 | 甘特怎么画 |
|---|---|
| 排了 | 真正的分段（G-04），位置来自 `startOffsetMinutes` |
| 没排 | 不切段，画一条**进度填充**：已完成阶段数 / 总数 |

进度说的是「三件里做完了一件」，不说「什么时候做的」——
这是这份数据支持得起的全部结论。

> 「没有阶段」与「一个都没做」是两回事：前者 `progress` 为 `null`
> （压根不画），后者为 `0`。画成一样的话，一条没拆阶段的任务
> 看起来像是一件都没开始。

### 4.4 性能

甘特是最容易掉帧的视图（NFR-PERF-02）。措施：

1. 用 `CustomPainter` 一次性绘制条形层，**不是**每个条一个 Widget。
2. 只绘制可见时间窗 ± 一屏；滚动时按窗口增量重算。
3. 布局计算（泳道分列、重叠消解）是纯函数，可独立单测 + 基准测试。
4. 缩放时不重算布局，只做变换；缩放结束后再按新粒度重算。

### 4.5 布局算法必测用例

| # | 用例 | 期望 |
|---|---|---|
| G-01 | 单泳道单任务跨 3 天 | 一根连续条，高度 = 3 个时间单元 |
| G-02 | 同泳道两任务时间重叠 | 分成 2 列，各占半宽 |
| G-03 | 同泳道 4 个重叠 | 3 列 + 折叠指示 |
| G-04 | 3 阶段任务 | 3 段，颜色各异，段间有缺口，总长 = 任务跨度 |
| G-05 | 阶段偏移超出任务结束 | 跨度用领域层的 `effectiveEnd`（见[数据模型 §4.7](../02-domain/data-model.md#47-任务的有效跨度由领域层派生不是甘特图的私事)），**且时间轴/列表对同一任务必须得到同一个跨度** |
| G-06 | 重复任务在窗口内多次发生 | 每次发生一根独立的条 |
| G-07 | 窗口边界处被截断的任务 | 条延伸到边界，边缘渐隐，不显示为「结束」 |

## 5. 视图切换的一致性（FR-VIEW-05/06）

| 场景 | 期望行为 |
|---|---|
| 在列表设筛选「只看工作」→ 切甘特 | 甘特只显示工作泳道 |
| 在日历选中 9/20 → 切时间轴 | 时间轴显示 9/20 |
| 在时间轴滚到下午 → 切日历 → 切回 | 仍在下午的位置 |
| 在甘特缩放到「周」→ 切日历 | 日历切到周视图（共享 `granularity`） |
| 一个末阶段超出 `endDate` 的任务 | 甘特与时间轴显示**同一个**跨度（都用领域层 `effectiveEnd`，不各自计算） |

这四条是集成测试 J-01 的一部分，**必须自动化验证** —— 手工验证这种跨视图状态最容易漏。

## 6. 默认视图与启动

配置项 `view.defaultView`，默认「列表」（对新用户最易理解）。
冷启动直接进入该视图，不经过中转页（NFR-PERF-01：1.5s 内可交互）。

## 7. 外壳与导航

### 7.1 四视图**不是**四个目的地

结构上有两种选法，选第二种：

| | 底部导航四个 Tab | 一个外壳 + 视图切换器 |
|---|---|---|
| 语义 | 「去别的地方」 | 「换个看法」 |
| §5 的状态保持 | 要额外机制（每 Tab 自己的 Navigator、状态恢复） | **天然成立**，压根没换页 |
| 筛选条 / FAB | 每个 Tab 各挂一份，或提到外面 | 本来就在外壳上，只有一份 |
| 加一个视图 | 动路由表 + 动 Tab 栏 | 枚举加一项 + 注册一个构建器 |

决定的理由是第一行：**四视图是同一份数据的四种呈现，不是四个目的地。**
切过去之后筛选、聚焦日期、选中态全都保持（FR-VIEW-05/06）——
那是「换个看法」的语义。底部导航暗示的是「离开这里去那里」，
与「切完之后一切照旧」互相打架。

第二行是这个选择的直接红利：§5 那四条一致性要求在这个结构下
**不需要任何机制**就成立，因为根本没有发生路由切换，
共享状态一直活在外壳上。反过来，Tab 方案要为每个 Tab 维护
独立 Navigator 与状态恢复，而那正是「跨视图状态」最容易漏的地方。

### 7.2 路由表

| 路由 | 页面 | 说明 |
|---|---|---|
| `/` | 外壳（当前视图由 `ViewKind` 决定） | 冷启动直达，不经中转页（§6）|
| `/task/new` | 任务编辑器（新建） | 可带 `date` 查询参数，供「长按空白快速新增」|
| `/task/:id/edit` | 任务编辑器（编辑） | |
| `/settings` | 设置 | 独立页，**不是** Tab |

**视图切换不产生路由**。`/` 始终是 `/`，切视图改的是外壳上的一个状态。
代价是视图不可深链（`/gantt` 这种地址不存在），收益是 §5 白得。
V2 小组件点击要跳到具体任务，走的是 `/task/:id/edit`，不受影响。

### 7.3 视图注册表

新增一个视图 = **枚举加一项 + 注册一个构建器**，不动路由表、不动外壳
（NFR-MAINT-03）。

未注册的枚举值不是运行时崩溃，也不是静默空白页 ——
由架构守卫测试在**编译期之后、运行之前**判失败：
枚举里的每一项要么有构建器，要么在「已知未实现」名单里显式列出。

> 这条是给 M3 用的。M2 只有列表一个视图，此时最容易发生的事情是
> 写一个只对一个视图成立的外壳，等 M3 加视图时才发现要重写。
> 注册表让「只有一个视图」和「有四个视图」在结构上是同一件事。

### 7.4 默认视图取不到时怎么办

`view.defaultView` 存的是枚举名。用户降级安装、或配置文件被改坏时，
可能读到一个当前版本不认识的名字。

**不崩、不空白**：回落到列表视图（§6 的默认值），并且这个回落
必须是**显式的一条分支**，不是 `firstWhere` 抛异常后被谁吞掉。
