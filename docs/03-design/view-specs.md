# 四视图规格

> 对应需求 FR-VIEW-01..07。
> 四个视图**共享同一份数据源与筛选状态**（`visibleOccurrencesProvider`），各自只负责布局与交互。
> 这是 FR-VIEW-05/06 能成立的架构前提，见[架构总览](../01-architecture/overview.md) §3。

## 0. 共享层

### 0.1 共享状态

```dart
ViewSharedState {
  DateTime focusedDate;        // 当前聚焦日期，视图切换时保持
  FilterSpec filter;           // 分类/标签/优先级/状态/关键词，视图切换时保持
  String? selectedOccurrenceId;
  TimeGranularity granularity; // 日/周/月，甘特与日历共用
}
```

### 0.2 共享数据源

```dart
// 输入: 可见时间窗 + 筛选  →  输出: 已展开、已应用例外、已排序的实例
Stream<List<Occurrence>> visibleOccurrences(DateRange window, FilterSpec filter)
```

每个视图声明自己需要的 `window`（时间轴要 1 天，日历月视图要 1 个月 + 前后补齐），
其余完全一致。**禁止**任何视图自己查库。

#### 0.2.1 列表的窗口，以及窗口装不下的两类东西

实现时出参不是 `Occurrence` 而是 `TaskOccurrence`（`(任务, 可选的某一次)`），
因为有两类东西 `Occurrence` 表达不了，而它们都不能从列表里消失：

| | `Occurrence` 能表达吗 | 为什么不能丢 |
|---|---|---|
| **没有日期**的任务 | ✘ `start` 是必填墙钟 | §2.1 专门有「无日期」这一组；FR-TASK-01 说仅填标题即可保存 |
| 窗口**之外**的一次性任务 | ✘ 窗口外不产出 | 「明年那件事」从列表里消失，会让人以为它丢了 |

于是展开的规则是：

- 无日期 → 一行，`occurrence` 为 null；
- 不重复 → 一行，**不看窗口**（它只有一次，不存在展不完的问题）；
- 重复 → 见下。

#### 0.2.2 重复任务：逾期的全留，未来只留「下一次」

一度是「窗口内每次一行」。实测下来那不能用：一条「每天」在列表里就是
**六十一行**，逾期组还会往上堆 —— 那不是一份计划，是一份日历的转录。

| 那一次 | 显示吗 | 为什么 |
|---|---|---|
| 没做完，日期在今天之前 | **留着**（逾期组） | 漏交一次房租不该无声消失 |
| 没做完，今天或以后 | **只留最早的一条** | 那就是「下一次」 |
| 已完成，今天或以后 | 留着 | 刚勾掉的卡片不能立刻消失（[§8.1](design-system.md#81-任务卡片最重要的组件)），要给撤销留时间 |
| 已完成，且已是过去 | 不留 | 否则天天堆划掉的行 |
| 已跳过 | 不留 | FR-TASK-05 验收：「不出现在任何视图」 |

于是勾掉今天那次之后，**下一次当场顶上来**，而刚勾的那张划掉的卡片
还在原位可以撤销。跳过同理。

最后两栏被折叠掉的那些，**只有在筛选条里显式勾「已完成」/「已跳过」
时才回来**（`expandForList` 的 `includeCompleted` / `includeSkipped`）。
这是它们唯一的入口 —— 没有这条路的话，做完或跳过的那些次就再也
找不回来，与「到某天为止」那条死路是同一种毛病。

#### 0.2.2.1 三套展开，各答各的问题

| 函数 | 谁用 | 范围 | 折叠 |
|---|---|---|---|
| `expandInWindow` | 日历、甘特 | 给定窗口 | 不折叠，窗口内一次不落 |
| `expandForList` | 列表 | 相对今天 | 逾期全留、未来留一次（[§0.2.2](#022-重复任务逾期的全留未来只留下一次)） |
| `expandForAgenda` | 时间轴 | 相对今天 | 逾期留一条、今天起补满两条（[§1.2.1](#121-本次和下次是哪两次)） |

合成一个带开关的函数的话，「日历为什么少了几天」会变成一道
要读策略分支才答得上的题。

`expandInWindow` 问的是「这段时间里都发生什么」，答案由日期决定，
不掺任何取舍。它有两条与列表不同的规矩：

- **没有日期的任务不进来** —— 它不落在任何一天上（列表另有「无日期」组）；
- **按覆盖区间收，不按开始日期** —— 「9/1 到 9/30 的项目」在 9/15
  那天必须在，昨晚 22:00 的值夜在今天早上也必须在。

重复的跨天任务另有一道手续：引擎是按**开始日期**筛的
（`window.contains(occ.start.date)`），所以展开时要往前多要几天，
多要的天数按**任务自己的时长**算，上限 62 天
（`_maxSpanDays`，性质同 `lookaheadDays`：刻意的上界，不是遗漏）。

这个上界由 `expand_in_window_test.dart` 的**两条边界用例**夹住：
跨 62 天的在、跨 63 天的缺席。少了后一条，把上限改成 400 全绿 ——
而那会让每条重复规则都多展开三百多天。

#### 0.2.3 三个窗口常量（`ListHorizon`）

| 常量 | 值 | 决定什么 |
|---|---|---|
| `pastDays` | 14 | 逾期最多回溯多久。再长的话，搁置三个月的每日任务会堆出九十行 |
| `futureDays` | 60 | 往前找「下一次」时多远以内算便宜。它**不再决定行数** |
| `lookaheadDays` | 732 | 兜底。「每年 5 月 20 日」在九月时下一次在八个月后，只看 60 天的话**整条任务从列表里消失** |

比 `lookaheadDays` 还稀疏的规则（每三年）不显示「下一次」，只显示逾期的
那些 —— 这是刻意的上界，不是遗漏。

> 「每天」这类规则是无限的，而 §2.1 的「更远」字面上没有尽头 ——
> 两者不可兼得。折叠成「下一次」之后，「更远」组里装的就只有
> 一次性任务与各条规则的下一次了。

### 0.3 共享交互

| 交互 | 所有视图一致 |
|---|---|
| 点击实例 | 打开详情底部弹层 |
| 长按空白 | 在该时间点快速新增（FR-VIEW-07）—— 目前只有时间轴接了，见下 |
| 完成钮 | 就地完成 + 撤销 Snackbar |
| 顶部筛选条 | 同一个组件，同一份状态 |
| 悬浮新增按钮 | 常驻右下，**只在对着某一天的视图里**带日期，见下 |

#### 0.3.1 「带当前上下文」到底带什么

上下文分两层，都可以缺：

| 分量 | 谁给得出 | 给不出时 |
|---|---|---|
| 日期 | 时间轴 / 日历 / 甘特 —— 都有一个用户正看着的聚焦日 | 列表：它横跨所有日期 |
| 时刻 | 时间轴长按（对齐到刻度，**向下取整**） | 其余入口 |

**列表里的加号不带日期，这是刻意的。** 一律盖上「今天」的话，
「随时」这一档就再也建不出来了 —— 而它是 FR-VIEW-01 点了名的一档。
判据写在 `ViewKind.anchorsToDay` 上。加号先前无条件带上聚焦日，
两条既有测试（滑动推迟里的「没有日期的任务」、设置页里的「无日期分组」）
一起变红，指的就是这件事。

时刻**向下对齐到整格**，不是就近对齐：验收原话是
「在时间轴 14:00 处长按新增，新任务默认时间为 14:00」——
手指落在 14:00 那一格里的任何位置，用户说的都是 14 点。
就近的话，按在格子下半部会跳到 15:00，而他明明是对着「14:00」那行字按的。

只给日期时建出来的是**全天**任务，不是当天 00:00：
从日历翻到某天点加号，用户表达的是「这一天」，
补一个 00:00 会让它跑到时间轴最顶上去。

## 1. 时间轴视图 TimelineView（FR-VIEW-01）

> **这一节重写过一次。** 第一版是「单日 24 小时刻度尺 + 按时刻定位的块」，
> 用户看过之后要的是另一样东西：
>
> > 时间轴应该是按任务/阶段的开始时间卡片排列下来（无日期的不进视图）。
> > 类似左侧是竖向时间轴右侧是任务/阶段卡片，**时间是跳跃的**。
>
> 差别不是样式，是**排布的依据**。旧规格连同 `view.timelineTickMinutes`
> 一起作废（配的是刻度尺的比例，而刻度尺没了）。

### 1.1 布局

```
┌─────────────────────────────────────────┐
│ 9月9日 今天                              │ ← 日期分隔
│ 09:00 ●┃ ┌────────────────────────────┐ │
│        ┃ │ ▎晨会                       │ │
│        ┃ └────────────────────────────┘ │
│ 10:30 ●┃ ┌────────────────────────────┐ │
│        ┃ │ ☐▎写方案 · 收集材料           │ │ ← 阶段各占一行
│        ┃ └────────────────────────────┘ │
│ ─────── 现在 14:32 ───────────────────── │
│ 9月10日 明天                             │
│ 全天  ●┃ ┌────────────────────────────┐ │
└─────────────────────────────────────────┘
```

### 1.2 关键规则

| 规则 | 说明 |
|---|---|
| **纵轴是跳的** | 只在有东西的时刻打点，**空白时段不占高度** |
| 范围 | 所有未完成的，一路排下去；不是单日 |
| 无日期任务 | **不进视图** —— 它不落在任何一条时间线上（列表另有「无日期」组） |
| 全天任务 | 排在当天最前，时间栏写「全天」，不写占位的 00:00 |
| 阶段 | **各占一行**，按自己的开始时刻排；同一时刻时任务排在自己的阶段前面 |
| 没排时间的阶段 | 不成行 —— 没有开始时刻，硬给一个是编造（同 [§4.3.1](#431-没排时间的阶段给进度不给编造出来的段)） |
| 重复任务 | 只出**本次和下次**（见 [§1.2.1](#121-本次和下次是哪两次)） |
| 时间栏 | 同一时刻只写一次；换一天重新写 |
| 「现在」 | 只在**它两边都有东西**时出现，每分钟更新 |
| 逾期 | 日期分隔与卡片用 overdue 色，不加感叹号也不铺红底（[design-system §2.4](design-system.md)） |
| 聚焦日 | 不筛内容，只决定**滚到哪一段**（FR-VIEW-06，见 [§5](#5-视图切换的一致性fr-view-0506)） |

空白时段不占高度是它与日历/甘特的分工所在：那两个回答「这段时间有多满」，
时间轴回答「**接下来依次是什么**」。一天里只有两件事时，
前者该画出大片空白，后者不该。

#### 1.2.1 「本次和下次」是哪两次

用户的原话是「重复任务只出本次和下次」。直译成「最早的两次未完成」
会在一处出错：一条搁下两周的每日任务，最早的两次都在半个月前，
于是**今天那次反而看不见** —— 而这个视图要回答的正是「接下来是什么」。

所以那个「两次」**只管今天起的那一侧**：逾期的全部保留，
今天起的按顺序留两条。

| 情形（今天 9/9） | 出哪几条 |
|---|---|
| 每日，8/26 起全没做 | 8/26…9/8 每一条，加 9/9、9/10 |
| 每日，逾期的都补上了 | 9/9、9/10 |
| 每周一，9/2 漏了 | 9/2、9/9、9/16 |
| 规则已经结束，只剩逾期的 | 全部逾期的那些 |

**逾期为什么不折叠。** 中间有过一版是「逾期只留最早一条」（一条足够
说明「你欠着」），用户看过之后要求全留：漏了几次和漏了一次是两件事，
而折叠之后这两者长得一样。这不是技术判断，是需求持有者的决定。

代价是有界的：往回只展开 `ListHorizon.pastDays`（14）天，
所以一条每日任务最多堆出十四行，不会无限长。

窗口沿用 `ListHorizon`（[§0.2.3](#023-三个窗口常量listhorizon)），与列表
**共用同一个**「多久以前算逾期」—— 各定各的话，同一条漏做的任务
会在列表里还在、在时间轴上已经不见。

#### 1.2.2 加号不带日期

议程横跨多天，用户在这儿点加号没有指向任何一天。一律盖上「今天」的话，
「随时做」这一类任务就再也建不出来了（FR-TASK-01 点了名的一档）——
与列表同一条理由，判据都在 `ViewKind.anchorsToDay` 上。

FR-VIEW-07 验收原话点的是时间轴（「14:00 处长按新增」），那是单日刻度尺
才有的画布。这条交互留在**甘特**上（纵轴仍是时间），日历那边的
对应形态是点某一天。

### 1.3 空态

插画 + 「接下来没有排着的事，要加点什么吗？」+ 新增按钮（不带日期）。

## 2. 列表视图 TaskListView（FR-VIEW-02）

### 2.1 分组维度（可切换，配置项 `view.listGroupBy`）

| 维度 | 分组顺序 |
|---|---|
| 按日期（默认） | 逾期 → 今天 → 明天 → 本周 → 更远 → 无日期 |
| 按分类 | 分类自定义 `orderIndex` |
| 按优先级 | 紧急 → 高 → 普通 → 低 → 无 |
| 按状态 | 进行中 → 待办 → 已完成 |

### 2.2 组内排序（配置项 `view.listSortBy`）

时间升序（默认）/ 优先级降序 / 创建时间 / 手动（`sortOrder`，支持拖拽）

### 2.3 筛选

分类（多选）、标签（多选）、优先级（多选）、状态（多选）、关键词、日期范围。
**条件可叠加**：维度之间取交集，维度之内取并集（`FilterSpec`）。

#### 2.3.1 一个维度一个按钮，点开是多选弹层

第一版是一条横向滚动的 Chip 条 —— 清除 + 三个状态 + 五个优先级 +
分类若干，十来个 Chip 排成一行。用户的原话：

> 还要改造下顶部的筛选，改为下拉或抽屉或其他形式的多选器，
> 按 状态/分类等等分为多个选择器。

那条 Chip 条有两个问题，都不是审美问题：

- **看不出维度。** 「已完成」「紧急」「工作」排在一起，读起来像一串
  平级开关 —— 而它们之间是交集、维度内部是并集。这条规则写在
  `FilterSpec` 的注释里，界面上一个字都没有。
- **够不着。** 分类多一点，后面几个要横向滚两三屏，而横向滚动条上
  没有任何「后面还有」的提示。

现在顶部是 `状态 / 优先级 / 分类` 三个按钮，各带**选了几项**；
点开是那一维的多选弹层（`FilterSheet`），弹层里逐项勾选、
有「清空这一维」，收起要按「完成」——**不会点一下就关**，
多选的意义就在于连着选几项。

| 规则 | 说明 |
|---|---|
| 计数写进标签 | 「状态 2」，不做成角标 —— 角标是纯图形，读屏读不出来（NFR-A11Y-01） |
| 只放设得出来的项 | `inProgress` 没有任何入口，摆出来是个筛不出东西的按钮 |
| 「已跳过」必须在 | 跳过的那一次不出现在任何视图（FR-TASK-05），**这是唯一的反悔入口** |
| 「清空」只清这一维 | 牵连别的维度的话，用户会以为筛选整个坏了 |
| 「清除筛选」 | 三维一起清，只在筛了东西时出现 |

「已生效条件的展示」就是按钮上的那个计数，没有再单做一条展示栏 ——
两处各画一遍的话它们迟早不同步，而用户会相信离他更近的那一处。

### 2.4 交互

| 手势 | 默认动作（可在配置中改，`behavior.swipeLeft/Right`） |
|---|---|
| 右滑 | 完成 |
| 左滑 | 推迟到明天 |
| 长按 | 进入多选模式，批量操作 |

滑动的可选动作：`complete` / `postpone` / `delete` / `none`。

`delete` 一度**不在里面**，理由是「滑一下就把整条重复任务删掉，
在误触时代价太大，而当时唯一的退路是一条 Snackbar —— 划走了就找不回来」。
回收站做出来（FR-TASK-08）之后这个理由消失了：删除是软删除，
进回收站，随时能恢复。所以补上。

> 这段留着不是为了记「当时没做」，是为了记**判据**：
> 一个动作能不能放进滑动手势，看的是「误触之后有没有回头路」。

滑动是最容易误触的手势（列表本来就要上下滚），所以**每次滑动都配一条
撤销 Snackbar**（§0.3）。撤销闭包由动作本身给出，不是界面层再算一遍：
「推迟」的撤销要回到**原来那天**，而那个值只有动作知道；
「完成」的撤销要回到**切换之前**的状态，再调一次切换等于又切回去。

推迟的粒度目前固定是**一天**。`behavior.postponeMinutes` 没进注册表 ——
按分钟推迟还没有消费者，而没有消费者的声明就是一个改了没反应的开关。

「逾期」分组默认折叠并显示计数 —— 展开是用户的主动选择，避免一打开就被一堆红字压住。

#### 2.4.1 多选：批量动作复用单行动作

「完成一行」在重复任务上不是改 `tasks.status`，而是写一条例外；
「删一行」是软删整条任务。批量若自己再判一遍「这行是某一次还是整条」，
两处迟早分叉 —— 而分叉的表现是**「单个勾完成好好的，
批量勾完成把整条重复任务标完成了」**，用户根本不会想到去比这两条路。

所以批量只做三件事：把选中的 id 还原成行、逐行调既有动作、
把它们各自给出的撤销闭包攒成一条。

| 决定 | 理由 |
|---|---|
| 选中集合存**行 id**，不存 taskId | 一条规则展开出的几行共用 taskId，存 taskId 会「选一行选中好几行」 |
| 模式 = 选中集合非空，不另存开关 | 「模式开着但一个都没选」是个能表达、却没人想清楚该长什么样的状态 |
| 多选模式下完成钮不响应 | 一个框在两种模式里表示两件事，是最容易点错的那种设计 |
| **每个批量动作各自要有撤销用例** | 「删除有撤销」不蕴含「完成也有」—— 变异演练里这条真的漏过 |
| 选中态**加边框**，不只是换底色 | 低饱和配色下一层浅底与未选中几乎分不出来（§8.1） |

批量动作**一定要给撤销**：单行滑动都配了，而批量一次动的是十几条，
误触的代价按条数放大。

**批量与单行支持的动作要对齐**：滑动可配的三个（完成 / 推迟 / 删除）
批量都有。一度只有完成与删除 —— 判据是评审给的：
「批量路径有没有任何一步是单行路径不走的，以及有没有一方支持、
另一方不支持的动作」。推迟时**要说清真的挪了几条**：
没有日期的推不了，选了五条只动了三条却什么都不说，用户会以为全动了。

## 3. 日历视图 CalendarView（FR-VIEW-03）

> ### 周视图去掉了（用户决定）
>
> 规格原来定的是「月视图 + 周视图」，界面上配了月/周切换。
> 用户看过之后要求去掉：「不需要『周』固定使用月即可」。
>
> 空出来的位置给了**当前月份标题 + 左右翻月** —— 那是同一次反馈里
> 更要紧的一条：「看不出当前月份，左右滑动后就看不出现在几月份」。
> 格子里只有日号，翻过去长得一模一样，划两下之后没有任何线索。
>
> `granularity` 仍然是共享状态，只是**日历不再是它的显示方之一**；
> 甘特那边的日/周/月照旧（FR-VIEW-04 的验收原话）。
> 实现上保留了 `calendarIsMonthProvider`（恒为 true），
> 将来若要恢复周视图，改那一处就够。

### 3.1 结构

上半月历格子 + 下半选中日列表，比例可拖拽（记住用户选择）。

| 模式 | 说明 |
|---|---|
| 月视图（默认） | 6 行格子；格子内显示最多 3 个色点 + 「+N」 |
| 周视图 | 一行 7 格，格子内显示任务标题缩略 |

### 3.2 关键规则

- 一周起始日来自配置项 `view.firstDayOfWeek`，默认周一。
- 今天：主色描边圆；选中：主色实心圆 + `text.onBrand`。
- 色点颜色取分类色；**同时**在下方列表显示分类名（颜色非唯一载体）。
- 全天/跨天任务在格子顶部以横条贯穿，连续多日不断开。
- 左右滑动切月，**跟手且带惯性**；`reduceMotion` 时改为无动画直接切换。

#### 3.2.1 跟手这一条，改的是数据层

第一版是「松手才切」：`onHorizontalDragEnd` + `AnimatedSwitcher`，
手指在屏幕上拖的时候什么都不动。那不叫惯性 —— 屏幕上没有任何东西跟着手指。

跟手要求**相邻月份同时画得出来**，而布局原本只按聚焦月算一份。
所以先把 `calendarLayoutProvider` 拆成按月的 family
（`calendarLayoutForProvider`，键是 `YearMonth`），格子才换得成 `PageView`。
**界面上的一句「跟手」，落在数据层是「一份变多份」。**

按月拆而不是按周/按天：横条的层号本来就要在一整行里统一分配，
而「一整月」正好是这件事的自然边界（§0.2 那段的同一条理由）。

页号取「距某个固定锚点几个月」。锚点必须固定 —— 拿「今天」当锚点的话，
跨零点时所有页号会整体平移一格。页数是刻意的上界（锚点前后各约两百年），
同 `ListHorizon.lookaheadDays` 那条。

### 3.3 基础组件：**自己搭，不用 `table_calendar`**（决定已变更）

原定用 `table_calendar 3.2.1` 当骨架，「只为省掉日期网格与滑动分页的边界处理」。
做到这一步时去读了它的源码，那个前提不成立：

**它的 builder 全是按格子调的** —— `FocusedDayBuilder`、`DayBuilder`、`MarkerBuilder`
都只拿得到一个 `day`。连 `rangeHighlightBuilder` 也是（签名是 `(context, day, isWithinRange)`，
在每格自己的 `LayoutBuilder` 里调用）。它自己那条跨天高亮，就是**每格画一条到边的横条
拼出来的**，两端各留 50% 边距。

而 §3.2 要的是「全天/跨天任务以横条贯穿，**连续多日不断开**」，且同一行里可能有多条
不同层的横条。在按格子的模型下，这要么把 `rangeHighlightBuilder` 挪作他用去画一整摞层，
要么每格自己拼——两条路都是在跟这个库的模型对着干，而拼接处的半像素缝没有测试盯得住。

自己搭之后：**一周就是一个 widget**，横条是 `Stack` + `Positioned(left: i*w, width: n*w)`，
不存在缝。而它本来要省的两件事：日期网格是 `month_grid.dart`（纯函数，带 16 条用例），
滑动分页是一个 `PageView`。

依赖已从 `pubspec.yaml` 移除。

> 这条记在这里而不是悄悄改掉：原来的选择是有理由的（省边界处理），
> 变更的理由也很具体（那个库的模型与这条硬需求冲突）。
> 只留结论不留过程的话，下一个人会重新提议用 `table_calendar`。

## 4. 竖向甘特视图 GanttView（FR-VIEW-04）

这是最独特也最难的视图，单独展开。

### 4.1 为什么是竖向

手机是竖屏长条。横向甘特在手机上只能看到 2–3 天，失去「纵览」意义。
**竖向**：时间从上往下流动（与阅读方向一致），泳道横向排列，一屏能看两周以上。

### 4.2 布局

```
        │ 学习    │ 工作    │ 生活    │   ← 泳道表头（吸顶）
────────┼─────────┼─────────┼─────────┤
 9/8 一 │ ┃阶段1  │ ┃周报   │         │
 9/9 二 │ ┃       │ ┗━━━   │ ┃健身   │
 9/10三 │ ┃       │         │         │
 9/11四 │ ┣阶段2  │ ┃方案   │ ┃健身   │   ← 阶段分段换色
 9/12五 │ ┃       │ ┃       │         │
 9/13六 │ ┗━━━   │ ┗━━━   │         │
────────┴─────────┴─────────┴─────────┘
   ↑ 时间轴（吸左）
```

### 4.3 关键规则

| 规则 | 说明 |
|---|---|
| 泳道维度 | 配置项 `view.ganttLaneBy`：按分类（默认）/ 按任务 / 按标签 |
| 时间粒度 | 日 / 周 / 月三档，双指缩放或顶部切换（见 [§4.3.2](#432-双指缩放一次手势只换一档)） |
| 阶段条 | 一个阶段事项画成**一根连续的条**，按阶段分段换色，段间有 2dp 缺口 |
| 进度 | 已完成的阶段段落填实，未完成为半透明 + 左边线（不是虚线边，见下） |
| 今日线 | 横贯所有泳道的水平线 |
| 重叠 | 同泳道同时段多任务时，泳道内再分列（最多 3 列，超出折叠） |
| 无日期任务 | 不出现在甘特图（甘特的本质是时间跨度） |
| **没排时间的阶段** | **不切段**，改画一条进度填充，见 §4.3.1 |
| 点击段落 | 直接定位到该阶段，可就地标完成 |

> **「就地」永远发生在某一次上。** 重复任务的阶段状态按发生分别存
> （FR-TASK-07、[数据模型 §3.5](../02-domain/data-model.md)），
> 所以勾选的入口在**单次动作弹层**里，不在编辑器里 ——
> 编辑器编的是整条任务，在那儿勾等于把每一周都标成完成。

### 4.3.2 双指缩放：一次手势只换一档

三档是**离散**的（窗口跨度 14 / 35 / 90 天），不是连续缩放。所以捏合
不是「实时改比例尺」，而是「越过一个阈值就跳一档」。

| 规则 | 值 / 说明 |
|---|---|
| 方向 | 张开 = 放大 = 看得更细（→ 日）；捏合 = 看更长的跨度（→ 月） |
| 阈值 | 间距变化 1.35 倍。再小则两指按住的抖动会误换档 |
| **一次手势只换一档** | 手指一路张开会连着跨过两个阈值，用户想的是「放大一点」，得到「放大到底」是两回事 |
| 到头 | 夹住，不回绕 |

**顶部那排日/周/月切换必须留着。** 捏合是个纯手势：读屏用户做不出来，
界面上也没有任何东西提示它存在。它是快捷方式，不是唯一入口
（同 NFR-A11Y-01「颜色/图标不单独承载信息」的那条思路）。

> **单指竖划不受影响。** 加了 `onScaleUpdate` 之后，缩放识别器会和滚动
> 那边的竖向拖动一起进手势竞技场 —— 它要是赢了，甘特就再也滚不动了。
> 有一条用例专门盯这件事。
>
> 换档本身**不需要**判「是不是两根手指」：单指时 `scale` 恒为 1.0，
> 两个阈值一个都够不着。一度写了那个判断，变异演练证明它什么也没做。

### 4.3.1 没排时间的阶段：给进度，不给编造出来的段

编辑器**默认不给阶段排时间** —— 用户加三个阶段、写个名字就存了。
那时把条按阶段数**均分**是很诱人的（三段各三分之一），但那是在编造数据：
它等于告诉用户「第一阶段在前三分之一结束」，而他从没这么说过。
与 §1.2「不替用户假设时长」是同一条原则。

所以分两种：

| 阶段有没有排时间 | 甘特怎么画 |
|---|---|
| 排了 | 真正的分段（G-04），位置来自 `startOffsetMinutes` |
| 没排 | 不切段，画一条**进度填充**：已完成阶段数 / 总数 |

进度说的是「三件里做完了一件」，不说「什么时候做的」——
这是这份数据支持得起的全部结论。

> 「没有阶段」与「一个都没做」是两回事：前者 `progress` 为 `null`
> （压根不画），后者为 `0`。画成一样的话，一条没拆阶段的任务
> 看起来像是一件都没开始。

### 4.4 性能

甘特是最容易掉帧的视图（NFR-PERF-02）。措施：

1. 用 `CustomPainter` 一次性绘制条形层，**不是**每个条一个 Widget。
2. 只绘制可见时间窗 ± 一屏；滚动时按窗口增量重算。
3. 布局计算（泳道分列、重叠消解）是纯函数，可独立单测 + 基准测试。
4. 缩放时不重算布局，只做变换；缩放结束后再按新粒度重算。

### 4.5 布局算法必测用例

| # | 用例 | 期望 |
|---|---|---|
| G-01 | 单泳道单任务跨 3 天 | 一根连续条，高度 = 3 个时间单元 |
| G-02 | 同泳道两任务时间重叠 | 分成 2 列，各占半宽 |
| G-03 | 同泳道 4 个重叠 | 3 列 + 折叠指示 |
| G-04 | 3 阶段任务 | 3 段，颜色各异，段间有缺口，总长 = 任务跨度 |
| G-05 | 阶段偏移超出任务结束 | 跨度用领域层的 `effectiveEnd`（见[数据模型 §4.7](../02-domain/data-model.md#47-任务的有效跨度由领域层派生不是甘特图的私事)），**且时间轴/列表对同一任务必须得到同一个跨度** |
| G-06 | 重复任务在窗口内多次发生 | 每次发生一根独立的条 |
| G-07 | 窗口边界处被截断的任务 | 条延伸到边界，边缘渐隐，不显示为「结束」 |

#### 4.5.1 七条用例管**位置**，四条不变量管**形状**

布局算法另有一组性质测试：随机造一屏输入，验四条不变量
（不越界、不倒挂、同列不重叠、折叠不丢）。两者**不可互相替代**：

| | 管什么 | 抓得到 | 抓不到 |
|---|---|---|---|
| G-01..G-07 | 位置 | 整体平移、整体拉伸 | 没人想到的输入组合 |
| 四条不变量 | 形状 | 重叠、越界、丢条 | **系统性平移** |

判据是实测出来的：把 `_place` 里的起止**整体平移一天**
（时长不变、不倒挂、不越界），红的全是 G 系列，
**四条不变量一条没红** —— 因为形状对位置一无所知。

> **所以：加一条不变量不能拿来换掉一条 G 用例。**
> 「性质测试更通用」这个直觉在这里是错的 ——
> 通用的是输入空间，不是断言维度。

这与[测试策略 §1.2](../05-engineering/testing-strategy.md) 那条
「一组断言可能一起绿，得有另一样东西钉住它们」是同一件事。

## 5. 视图切换的一致性（FR-VIEW-05/06）

| 场景 | 期望行为 |
|---|---|
| 在列表设筛选「只看工作」→ 切甘特 | 甘特只显示工作泳道 |
| 在日历选中 9/20 → 切时间轴 | 时间轴显示 9/20 |
| 在时间轴滚到下午 → 切日历 → 切回 | 仍在下午的位置 |
| 在甘特缩放到「周」→ 切日历 | 日历切到周视图（共享 `granularity`） |
| 一个末阶段超出 `endDate` 的任务 | 甘特与时间轴显示**同一个**跨度（都用领域层 `effectiveEnd`，不各自计算） |

这四条是集成测试 J-01 的一部分，**必须自动化验证** —— 手工验证这种跨视图状态最容易漏。

## 6. 默认视图与启动

配置项 `view.defaultView`，默认「列表」（对新用户最易理解）。
冷启动直接进入该视图，不经过中转页（NFR-PERF-01：1.5s 内可交互）。

## 7. 外壳与导航

### 7.1 四视图**不是**四个目的地

结构上有两种选法，选第二种：

| | 底部导航四个 Tab | 一个外壳 + 视图切换器 |
|---|---|---|
| 语义 | 「去别的地方」 | 「换个看法」 |
| §5 的状态保持 | 要额外机制（每 Tab 自己的 Navigator、状态恢复） | **天然成立**，压根没换页 |
| 筛选条 / FAB | 每个 Tab 各挂一份，或提到外面 | 本来就在外壳上，只有一份 |
| 加一个视图 | 动路由表 + 动 Tab 栏 | 枚举加一项 + 注册一个构建器 |

决定的理由是第一行：**四视图是同一份数据的四种呈现，不是四个目的地。**
切过去之后筛选、聚焦日期、选中态全都保持（FR-VIEW-05/06）——
那是「换个看法」的语义。底部导航暗示的是「离开这里去那里」，
与「切完之后一切照旧」互相打架。

第二行是这个选择的直接红利：§5 那四条一致性要求在这个结构下
**不需要任何机制**就成立，因为根本没有发生路由切换，
共享状态一直活在外壳上。反过来，Tab 方案要为每个 Tab 维护
独立 Navigator 与状态恢复，而那正是「跨视图状态」最容易漏的地方。

### 7.2 路由表

| 路由 | 页面 | 说明 |
|---|---|---|
| `/` | 外壳（当前视图由 `ViewKind` 决定） | 冷启动直达，不经中转页（§6）|
| `/task/new` | 任务编辑器（新建） | 可带 `date`、`minute` 查询参数（§0.3.1）。**读不懂一律当没给** —— 手敲错的链接只该让初值落空，不该让新建页打不开 |
| `/task/:id/edit` | 任务编辑器（编辑） | |
| `/settings` | 设置 | 独立页，**不是** Tab |

**视图切换不产生路由**。`/` 始终是 `/`，切视图改的是外壳上的一个状态。
代价是视图不可深链（`/gantt` 这种地址不存在），收益是 §5 白得。
V2 小组件点击要跳到具体任务，走的是 `/task/:id/edit`，不受影响。

### 7.3 视图注册表

新增一个视图 = **枚举加一项 + 注册一个构建器**，不动路由表、不动外壳
（NFR-MAINT-03）。

未注册的枚举值不是运行时崩溃，也不是静默空白页 ——
由架构守卫测试在**编译期之后、运行之前**判失败：
枚举里的每一项要么有构建器，要么在「已知未实现」名单里显式列出。

> 这条是给 M3 用的。M2 只有列表一个视图，此时最容易发生的事情是
> 写一个只对一个视图成立的外壳，等 M3 加视图时才发现要重写。
> 注册表让「只有一个视图」和「有四个视图」在结构上是同一件事。

### 7.4 默认视图取不到时怎么办

`view.defaultView` 存的是枚举名。用户降级安装、或配置文件被改坏时，
可能读到一个当前版本不认识的名字。

**不崩、不空白**：回落到列表视图（§6 的默认值），并且这个回落
必须是**显式的一条分支**，不是 `firstWhere` 抛异常后被谁吞掉。
