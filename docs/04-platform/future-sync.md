# 🔬 云端同步 / 恢复 / 邮件提醒（V3 预研）

> 分「已验证的事实」与「未验证的假设」两栏，**不得把假设当结论**。
> 用户需求原文包含三件事：云端同步、云端恢复、**云端能读取任务并在必要时发邮件**。
> 第三件决定了数据必须能被**服务端独立解析**，这是 V1 数据模型设计的直接约束来源。

## 1. ✅ 已验证的事实（V1 就已落实）

| # | 事实 | 依据 |
|---|---|---|
| F-1 | 每条可同步记录都带 `createdAt`/`updatedAt`/`deletedAt`/`revision`/`lastWriterId`/`remoteVersion` | [数据模型 §5](../02-domain/data-model.md) |
| F-2 | 所有写操作在同一事务内写入 `change_log`（outbox） | [数据模型 §3.11](../02-domain/data-model.md) |
| F-3 | 删除是墓碑不是物理删除，且墓碑会被导出 | [任务生命周期 §6](../02-domain/task-lifecycle.md) |
| F-4 | 导出是自描述 JSON，行 ⇄ JSON 字段一一对应，无客户端专有编码 | [数据模型 §6](../02-domain/data-model.md) |
| F-5 | 重复规则存的是 **RFC 5545 RRULE 字符串**，任何语言的成熟库都能解析 | [ADR-0004](../06-adr/ADR-0004-rfc5545-recurrence.md)，已实测往返无损 |
| F-6 | 计划时间存「墙钟 + IANA 时区」，服务端可独立算出绝对时刻 | [ADR-0005](../06-adr/ADR-0005-local-time-model.md) |

> F-5 与 F-6 合起来意味着：**服务端不需要移植任何客户端逻辑**，就能算出「这个任务下一次在什么时候发生」，
> 进而决定要不要发邮件。这正是用户那条需求能成立的技术基础。

## 2. ⬜ 未验证的假设 / 未决问题

| # | 问题 | 现状 |
|---|---|---|
| A-1 | 后端形态：自建服务 / 用户自持存储（WebDAV、S3、网盘） / 端到端加密备份 | **未定**。产品原则是「不建中心化账号」（[愿景 §4.3](../00-product/vision-and-scope.md)），倾向用户自持存储 |
| A-2 | 冲突解决粒度：整行 LWW 还是字段级合并 | 倾向整行 LWW（简单、可测），字段级留到证明确有必要时 |
| A-3 | 邮件发送方需要读到哪些数据 | 若走用户自持存储，「云端发邮件」需要一个愿意读该存储的服务，与 A-1 强耦合 |
| A-4 | 传输加密方案 | NFR-PRIV-02 要求传输前加密；密钥管理方案未定 |
| A-5 | outbox 回放的幂等性在真实并发下是否成立 | V1 有回放一致性测试，但只是单机顺序场景 |

## 3. 同步协议草案（待 A-1 定稿后细化）

### 3.1 基本循环

```
    ┌──── push ────┐                    ┌──── pull ────┐
    │              ▼                    │              ▼
本地 outbox ──► 上传未同步的变更     远端变更 ──► 本地应用
    │              │                    │              │
    └── 标记 syncedAt                   └── 冲突检测 ──► 解决
```

### 3.2 冲突检测

```
本地 revision/updatedAt/lastWriterId   vs   远端 revision/updatedAt/lastWriterId
        │
        ├─ 远端 remoteVersion == 本地记录的 remoteVersion  → 无冲突，直接推
        └─ 不等 → 冲突
                   ├─ 默认：LWW（updatedAt 大者胜；相等时 lastWriterId 字典序打破平局）
                   └─ 保留败方到 conflict_archive 表，永不静默丢数据
```

**「永不静默丢数据」是硬要求**：败方留档，UI 提供「这条有过冲突，查看另一版本」入口。
静默丢弃是同步类功能最伤用户信任的行为。

### 3.3 墓碑与清理

- 墓碑必须保留到「所有已知设备都已同步过该墓碑」之后才可物理删除。
- V1 没有设备列表概念，`data.trashRetentionDays`（默认 30 天）是简化替代。
  V3 需要引入设备注册表，否则会出现「删除被复活」。**这是必须在 V3 处理的已知缺口，现在写下来避免遗忘。**

## 4. 云端发邮件的最小可行形态

```
用户自持存储（含导出 JSON / 增量变更）
              │  只读
              ▼
     一个无状态的定时任务
              │  用任意语言的 RRULE 库展开
              ▼
       「未来 24h 内有哪些任务」
              │
              ▼
            发邮件
```

关键点：这个定时任务**只需要读 JSON + 一个 RRULE 库**，不需要理解应用的任何内部逻辑。
如果将来发现它需要移植客户端代码才能算出正确结果，说明 V1 的数据模型设计失败了 —— 这是一条可检验的判据。

## 5. V3 立项前必须先做的事

1. 定 A-1（后端形态）—— 这决定其余一切。
2. 写 `docs/schema/export-v1.schema.json`，并用**独立于客户端的脚本**（Python/Node）验证导出样例。
   这一步能提前证明 F-4 是真的。**建议在 V1 阶段就做**，成本低、价值高。
3. 把 §3.3 的墓碑清理缺口补上设计。
4. 设计密钥管理与端到端加密（A-4）。
