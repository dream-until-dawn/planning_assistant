# 测试策略

> **本项目的第一原则：永远绿的测试等于没有测试。**
> 一个测试的价值不在于它今天通过，而在于**当实现被改坏时它会失败**。
> 本文的大半篇幅在讲怎么证明测试真的有这个能力。

## 1. 测试有效性的判定标准

任何测试进入代码库前，作者必须能回答：

> **「如果我把被测实现改成什么样，这个测试会红？」**

答不上来的测试**不许合入**。这不是修辞 —— 见 §3 的执行机制。

### 1.1 明令禁止的测试反模式

| 反模式 | 例子 | 为什么是垃圾 |
|---|---|---|
| 无断言测试 | 只调用一遍函数，不 `expect` | 只能发现崩溃，发现不了错误 |
| 重言测试 | `expect(sut.value, sut.value)` | 恒真 |
| 对着实现抄 | 期望值由「跑一遍看输出」直接粘贴 | 实现错了测试跟着错 |
| 过度 mock | 把被测对象的协作者全 mock，断言的全是「调用了什么」 | 测的是实现细节，重构必红、改坏不红 |
| 捕获式断言 | `expect(() => f(), returnsNormally)` 作为唯一断言 | 同无断言 |
| 快照即真理 | golden 文件出错时直接 `--update-goldens` | golden 变成了「记录现状」而不是「校验预期」 |
| 条件跳过 | `if (Platform.isWindows) return;` 悄悄跳过 | 永远绿的经典手法 |
| **单样本推全称** | 用一条数据验证后写下「严格往返」「所有版本都…」 | 见 §1.2，本项目已经栽过一次 |
| **用 `assert` 表达不变量** | `assert(不变量)` | release 构建整条剥离 → debug 绿、线上零保护。见[横切关注点 §3.1](../01-architecture/cross-cutting.md) |

> 「对着实现抄」是最隐蔽的一种。对策：**期望值必须有独立来源** ——
> 手算、查 RFC、查规范文档、或用探针实测**并把实测过程记录在文档里**（如
> [环境探针结论](environment-notes.md) §2.1 中 `BYMONTHDAY=31` 的实测记录）。
>
> 更强的做法：**规范给期望值，探针只负责验证库是否符合规范**。
> 若反过来让库的实际输出决定期望值，库有 bug 时测试会跟着一起错。
> [重复引擎 §7](../02-domain/recurrence-engine.md) 的探针表因此专门加了一列「规范依据」。

### 1.2 单样本不能支撑全称结论（本项目的真实教训）

设计阶段我们用 `RRULE:FREQ=WEEKLY;INTERVAL=2;BYDAY=TU,TH` 测出 `roundtrip=true`，
就在三份文档里写下了「**RRULE 字符串严格往返**（已实测）」。

补一条带 `UNTIL` 的样本后，结论立刻被推翻：`toString()` 会丢掉 `UNTIL` 的 `Z` 后缀，
产出**不符合 RFC 5545** 的规则串。更糟的是 `rrule` 自己解析回来仍是等值的，
所以**任何只用本地往返做断言的测试都发现不了**，只有外部消费者（服务端、`.ics` 互通）会错 ——
而这两者正是我们选择 RRULE 格式的全部理由。

**然后这条结论又被推翻了第二次。** 改成「加 `isTimeUtc: true` 即严格无损往返」之后，
补上**多部件**规则的样本，发现编码器会重排部件：

```
输入 : RRULE:FREQ=MONTHLY;BYMONTHDAY=-1;UNTIL=20261231T155959Z
输出 : RRULE:FREQ=MONTHLY;UNTIL=20261231T155959Z;BYMONTHDAY=-1
```

第二次犯的是**同一个错**：第一次补样本时只补了 `FREQ=DAILY;UNTIL=…`，
仍然是单部件，于是「多加了一个样本」制造了已经充分验证的错觉。

**由此定下的规矩**：

1. 「严格 / 所有 / 总是 / 永远」这类**全称词**出现在结论里时，必须给出**覆盖各个分支的样本集**，
   而不是「多加一条样本」。判据是：**这个样本集覆盖了被测对象的哪几条代码路径 / 格式分支**，
   答不上来就等于没验证。
2. 往返测试要断言**正确的性质**，而不是最容易写的那个：
   - ❌ `encode(x) == 原始输入串`（字节等价）—— 对**部件无序**的格式会产生**假失败**，
     实测 6 个 RRULE 样本中有 4 个字节不等价，但全部合规且语义等同。
   - ✅ **合规性**：输出满足格式规范的硬性要求（如 `UNTIL` 必须带 `Z`）。
   - ✅ **语义往返**：`decode(encode(x)) == x`。
   - ✅ **规范形幂等**：`encode(decode(encode(x))) == encode(x)`。
   
   只有第一条能抓住「编码端出错、解码端宽容」这类缺陷；只有后两条能避免假失败。三者缺一不可。
3. 评审时看到「已实测」三个字，要问的是**测了几个样本、覆盖了哪些分支**，而不是「测了没有」。

### 1.3 第二个案例：样本来源本身会系统性地偏

同一个毛病换了个形状又出现了一次，而且这次**评审方和作者都栽了**。

事情是关于 `freezed 3.x` 允许哪个版本的 `analyzer`（结论见[技术栈 §6.1](../01-architecture/tech-stack.md#61-freezed-为什么必须是-4x完整论证)）：

| 轮次 | 谁 | 依据 | 结果 |
|---|---|---|---|
| 1 | 作者 | 求解器输出里的一段 | 写成「3.x 只到 analyzer 9–11」—— 那是 3.2.5 一段的值 |
| 2 | 评审方 | 本机 pub cache 里**唯一**的 `freezed-3.2.3` | 断定作者数字错、应为 `>=7.5.9 <9.0.0` —— 同样是单样本外推 |
| 3 | 评审方 | 用 WebFetch 让小模型概括 pub.dev API | 得到「3.x 全部是 `>=13.0.0 <15.0.0`」—— **与磁盘上的 pubspec 直接矛盾，是错的** |
| 4 | 双方 | 拉 pub.dev **原始 JSON** 全量枚举 16 个版本 | 才看清全貌，并发现一个谁都没料到的例外项 |

由此得到三条比 §1.2 更根本的规矩：

1. **「我手上恰好有的数据」不等于「能支撑结论的样本集」。**
   评审方不是懒得多测，是本机缓存里就只有那一个版本 —— 样本来源本身是偏的，而这种偏很难自觉。
   下全称结论前先问：**我的样本是怎么来的？这个来源有没有系统性地漏掉某一类？**
2. **经过概括的二手事实不能当依据**，哪怕来源是官方 API。
   上表第 3 轮就是活例：一次概括式抓取给出的答案与磁盘上的原始文件直接矛盾。
   拉原始数据自己解析，成本只多几十秒。
   > 本项目的 RFC 5545 引文最初也来自概括式抓取，后来回原始 RFC 全文（345KB）逐字核对过
   > （§3.3.10，"bounds the recurrence rule in an inclusive manner" 与
   > "…then the UNTIL rule part MUST be specified as a date with UTC time"），
   > 确认无误 —— 但**核对这一步不能省**。
3. **「数据完整」和「读过数据里的每一行」是两回事 —— 完整性会制造穷尽的错觉。**
   全量枚举后本可下一个漂亮的全称结论「freezed 3.x 任何版本都不允许 analyzer ≥ 13」，
   但 16 个版本里有一个 `3.0.0-0.0.dev` **根本不声明 analyzer 依赖** —— 不约束即不禁止，
   这句话字面上就是假的。正确写法是限定作用域：「**pub 会选取的**每个版本」。

   这一次的失效方式**与第 1 条不同，值得单独记**：
   第 1 条是拿不到别的样本（抽样偏差）；而这一次，**完整数据就在手上，
   那一行 `3.0.0-0.0.dev  analyzer: None` 就打印在结论上方几行**，
   写结论的人读过那段输出，然后写下了被它直接证伪的话。
   全量枚举带来的「我已经穷尽了」的踏实感，反而让人不再逐行看。

   **可操作的规矩**：下全称结论前，先把 `None` / 空值 / 缺字段 / 格式异常的行
   **单独挑出来看一遍**。工具也应当默认把异常项顶到眼前，而不是混在长列表里等人自己翻
   —— [`enumerate.py`](probe-artifacts/README.md) 就是这么做的。

   实际影响为零，但一句作用域不准的全称结论，将来一定会被人当成通则去用。

**复现脚本**：[`probe-artifacts/freezed-constraints/enumerate.py`](probe-artifacts/README.md)，
对任意包与依赖可复用，且会主动把「未声明该依赖」的例外项单独列出来。

### 1.4 校验工具本身必须先被证明能失败

**一个永远报「0 问题」的校验器，与一个什么都不做的校验器，在观测上无法区分。**

这不是假想。设计阶段的两个真实例子：

| 事件 | 后果 |
|---|---|
| 评审方的链接校验器把全角括号 `（）` 当作汉字保留进锚点 slug | 一次跑出 **14 条假失败**，差点据此提出一批不存在的问题 |
| 本项目的链接校验器连续五轮报「0 断链」 | 在被证明能失败之前，**这个 0 没有任何信息量** |

因此凡是「守卫」「校验」「断言基础设施」这一类东西，必须做到三条：

1. **自检**：喂已知的坏输入，断言**恰好检出**这些、且**不误报**好输入。
   工具自带 `--self-test`，进 CI，与被校验对象一起演进。
2. **对真实对象演示失败**：在真实对象上注入一处缺陷，确认变红且诊断正确，然后还原。
   **把失败输出留档**，而不是只说「我验过了」。

   ⚠️ 这一条**不是建立时做一次的仪式**。这类缺陷在视觉上与正常代码没有区别，
   code review 看不出来（§1.4.1 的那一行就是活例）——
   **变异演练是发现它的唯一手段**。因此工具每次实质性改动后都要重跑，
   与被校验对象一起纳入里程碑的变异演练清单（§3.1）。
3. **验收必须是双向的**：既要有「注入违规 → 变红」，也要有
   「**文档规定的正常写法 → 保持绿**」。

   只验前者对**「规则管得太宽」**这一类缺陷完全免疫 —— 它的症状是
   *正确代码变红*，而不是错误代码变绿。本项目的分层守卫就栽在这里：
   修「规则没在该生效处生效」时过冲，让守卫开始禁止 view-specs 明文规定的共享组件
   （见 [M0 执行记录 §2.1e](m0-record.md)）。
   把判定逻辑抽成纯函数、用**合成夹具表**双向驱动，比只跑真实文件早暴露一个里程碑。

4. **自检的期望值不能由被测逻辑自己产生。**
   否则「自检」本身就是一条永远绿的测试 —— 而它绿着的时候，
   你会以为整条链路都被证明过了。见下面 §1.4.1 的真实案例。

本项目的链接校验器 [`tool/check_doc_links.py`](../../tool/check_doc_links.py) 已完成这三步：

```
--- 自检：校验器能否正确失败 ---
  样本: 2 条好链 + 1 条坏文件 + 1 条坏锚点 + 1 条外链(应跳过)
  检出: ['ANCHOR_NOT_FOUND', 'FILE_NOT_FOUND']
  统计: 站内链接=4(期望4)  带锚点=2(期望2)
  结果: PASS —— 坏链能让它变红，好链不误报，全角括号锚点不误报

--- 对真实仓库注入坏链 ---
发现 2 处问题：
  FILE_NOT_FOUND     docs/README.md -> 00-product/does-not-exist.md
  ANCHOR_NOT_FOUND   docs/README.md -> 00-product/glossary.md#不存在的小节
exit=1                                    ← 还原后 exit=0
```

#### 守卫会以三种方式失效，症状与验法各不相同

| 失效方式 | 症状 | 靠什么发现 |
|---|---|---|
| 规则写错 / 漏写 | 错误代码变绿 | 注入违规 |
| **规则没在该生效处生效** | 错误代码变绿，**且无声** | **结构性断言**（如「每个文件都必须被分类」）—— 注入违规无效，因为违规文件本身在盲区里 |
| **规则管得太宽** | **正确代码变红** | **正向夹具**（文档规定的写法必须绿）—— 注入违规永远无效 |
| **规则没被套到某个桶上** | 错误代码变绿，且该文件**分类是成功的** | **完备性断言**（每个分类都必须有规则）—— 「未分类即违规」也发现不了它 |
| **约束是可达性的，而守卫看相邻性** | 错误代码变绿，且**每一条边都合法** | 传递闭包 / 符号级分析 —— 枚举式断言也发现不了它。⚠️ 本项目**尚未解决**，见 [M0 执行记录 §2.1g](m0-record.md) |

五种都真实发生在本项目的分层守卫上。前四种各花一轮修掉；**第五种只封了一个具体入口，通用解未做**。详见 [M0 执行记录](m0-record.md) §2.1b/§2.1d/§2.1e/§2.1f。

> 后两种的共同点：**规则内容全是对的**，问题在于规则没被套到那些文件上。夹具表验的是「规则内容对不对」，对这两种完全免疫 —— 只能靠把所有可能的路径与层键**枚举出来逐一确认**。

> 这与[路线图](../07-roadmap/roadmap.md) M0 的「故意写一个违反分层的 import，确认守卫测试变红」、
> M2 的「调淡一个颜色让对比度测试变红」是**同一条规矩**，只是对象不同。
> **规矩本身适用于它自己**：本节所依据的例子，都是先真的把工具弄红了才写下来的。

### 1.4.1 案例：为落实 §1.4 而写的自检，本身犯了 §1.1 的错

第一版自检里有这么一行：

```python
good_anchor = slugify("2.3 编码 RRULE 必须显式开启 `isTimeUtc`（强制）")   # ← 错
```

**期望值是被测函数自己算出来的。** slugify 一旦出错，标题那侧的 slug 与链接那侧的 anchor
会**同向偏移**、永远相等 —— 这条自检对 slug 算法的任何缺陷完全免疫。
它能验证的只是「链接匹配逻辑」，而**验证不了「slug 算法」**，后者恰恰是注释里声称要防的东西。

实测（把已知的 slug 缺陷注入副本）：

```
--- 自检：校验器能否正确失败 ---
  结果: PASS —— 坏链能让它变红，好链不误报，全角括号锚点不误报    ← 此刻这句是假的

文档 33 篇 · 站内链接 214 条
发现 18 处问题：ANCHOR_NOT_FOUND ...
```

**缺陷真实存在、真实生效，而专门用来锁它的那条自检，绿着。**

修法：期望值改为**手算的对照表**，且每条都另有独立佐证（仓库里存在指向该锚点、当前可达的真实链接）：

```python
SLUG_CASES = [
    ("2.3 编码 RRULE 必须显式开启 `isTimeUtc`（强制）", "23-编码-rrule-必须显式开启-istimeutc强制"),
    ("9. 评审要点（按重要性排序）",                      "9-评审要点按重要性排序"),
    ("6.1 `freezed` 为什么必须是 4.x（完整论证）",        "61-freezed-为什么必须是-4x完整论证"),
]
```

修完后按 §1.4 第 ② 条**两个方向都验证**：

```
注入同一缺陷：
  slugify 不符手算期望:
      期望 23-编码-rrule-必须显式开启-istimeutc强制
      实得 23-编码-rrule-必须显式开启-istimeutc（强制）
  slug 算法: FAIL（3 条手算样本，均含全角括号）
  exit = 2        ← 且不再继续扫仓库，避免用失灵的工具给出结论
无缺陷：
  slug 算法: PASS
  exit = 0        ← 不误报
```

> **为什么这条要单独立案**：工具的「绿」是**代人做保证**的 —— 本项目连续五轮拿它的
> 「0 断链」当结论用。普通测试错了只影响自己那条用例；工具错了，会让所有依赖它的结论
> 一起失去意义，而且**没有任何迹象**。
>
> 这个缺陷是评审方按 §1.4 第 ② 条对校验器**自己**做变异演练时发现的 ——
> 也就是说，§1.4 这条规矩在写下来的第二天就抓到了写它的人。
>
> 而它之所以能藏住，评审方的这句话说得最准：
> **「一个工具看起来已经被证明过了，是它最危险的时候。」**
> 正因为它带了 `--self-test`、打印了 PASS、注释里还写明了要防什么，
> 作者才在给评审方的消息里说它「不需要把关」——
> **是那层「已被证明」的外观让人停止了检查。**
>
> 补一条同样重要的：它是被**变异演练**抓到的，不是被 review 看出来的。
> 那一行 `good_anchor = slugify(...)` 在视觉上与其它行毫无区别，
> 有样本、有断言、有失败分支、注释齐全，**唯一的破绽是期望值的来源**。
> 所以 §1.4 第 ② 条的价值不在「建立时验一次」，而在于它是这类缺陷的唯一发现手段。

### 1.5 第三个案例：参数化一个维度、钉死另一个维度

M2 的任务卡片。断言型测试把**字号缩放**参数化到三档（1.0 / 2.0 / 2.8），
24 条全绿。转头生成 golden，6 张图全部溢出 3 像素。

判据没错 —— 「不许有 RenderFlex 溢出」这条断言本身是对的。
错的是**夹具的取值范围**：

| | 断言型夹具 | golden 画廊 |
|---|---|---|
| 字号缩放 | 1.0 / 2.0 / 2.8 | 1.0 / 2.0 / 2.8 |
| 时间标签 | `'14:00'`（钉死） | `'昨天 18:00'` |

同一个缩放下，这两个标签宽度差一倍。溢出要两个条件同时成立
（大字号 **且** 长标签），而夹具只让其中一个动。

这和 §1.2 是同一条规矩的不同形状，但**看出来的方式不一样**：

- §1.2 的破绽在**文字**里 —— 结论中出现「严格 / 所有 / 总是」。
- 本条的破绽在**代码形状**里 —— 一个 `for` 循环认真地穷举了一个维度，
  紧挨着的另一个维度是个字面量常量。读起来像「参数化测试」，
  而它证明的范围只有一条线，不是一个面。

**由此补一条判据**：写完参数化测试，把夹具里所有**字面量常量**列出来，
逐个问「这个值取别的会怎样」。答不上来的，要么参数化，要么在注释里
写清为什么这个维度不影响结论。

对本例，两个都做了：时间标签一并参数化；
另加一条**任何字体下都挤**的极端标签，验的是「挤了会下沉」这条规则本身，
而不是某个字体的度量恰好越过阈值
（见 [变异演练 M2](mutation-drills/M2.md) §1、§3）。

### 1.6 第四个案例：模型上有旋钮，界面上够不着

M2 的重复规则。`RecurrenceDraft` 的单元测试把七个字段测了个透 ——
编出的串是规范形、展开的日子对得上、三种结束条件互不相同，
外加对照组。856 条全绿。

界面上漏了三个控件：间隔、次数、结束日期。于是
`interval` 恒为 1、`count` 恒为默认的 10、`until` 永远是 null。
`describe()` 里那句「每 2 周」、`toRrule()` 里的 `INTERVAL=`、`UNTIL=`，
**用户一辈子也造不出来**。

测的是模型：给定一个 draft，它的行为对不对。
**没有一条问过：用户能不能造出那个 draft。**

这与 §1.2～§1.5 都不同 —— 那三条错在夹具的取值范围，
这条的夹具没问题，错在**被测对象选错了**：验的是链路的后半截，
而缺陷在前半截，两截之间没有任何一条测试跨过去。

同一形状此前出现过两次，当时没归纳：
配置项存进主题却没有控件读它（圆角档位）、
配置项有控件却没有消费者（默认视图）。都是**一条链路只接了一头**。

#### 更难看的是其中一条：死路

「到某天为止」选中之后规则必然非法 → 保存按钮永久灰着，
而页面上没有任何地方能选那个日期。**一条走进去出不来的路。**

当时确实有一条测试盯着它：

```dart
testWidgets('「到某天为止」没选日期时不给存', ...)
  expect(find.byKey(blockedReasonKey), findsOneWidget);   // 拦住了
  expect(await db.select(db.tasks).get(), isEmpty);       // 没落库
```

断言全对，而且它验的是一条真规矩。问题是它**停在了拦住的那一刻**。

> **判据**：凡是断言「这里会拦住用户」的测试，同一组里必须有一条
> 走完**解除拦阻**的路径。只验「拦住」的测试，与「这条路根本走不通」
> 无法区分 —— 而后者是缺陷。

#### 守卫：可达性探针 + 完备性对表

`test/presentation/recurrence_reachability_test.dart`：每个字段一条探针，
走真界面把它拨到**非默认值**，保存，然后看**落库的 RRULE 串**
变成了该变的样子（不看 draft、不看界面文案 —— 那两者在链路断掉时
依然好看，M2 的 `categoryId` 就是这么漏的）。

外加一条完备性守卫：扫 `RecurrenceDraft` 构造器的 `this.x` 取字段全集，
要求探针表**恰好等于**它。加了字段却忘了配控件，这条会红。

变异演练：把加减器的回调改成空函数、把日期选择器的回写删掉，
`interval` / `count` / `until` 三条各自变红，其余五条仍绿 ——
每条探针只对自己那个旋钮敏感。

### 1.7 用例末尾手写的收尾，失败时不会执行

上面那次变异演练顺带暴露了另一件事：变异跑出来是
**8 条里 3 条红**，但整轮花了 **6 分 33 秒**，后两条报的是
「did not complete」。

`disposeTree(tester)` 原本写在每条用例的末尾。断言一抛，那一句就不跑了 ——
树留在那儿带着 drift 的订阅和一个待触发的 `Timer(Duration.zero)`，
下一条用例撞上 `!inTest` 断言，再下一条超时十分钟。

**后果不是慢，是报错指错了地方**：一次真实的回归会表现成
「后面几条莫名其妙全红」，而真正坏掉的是第一条。

改成 `testAppWidgets`（`test/support/app_harness.dart`）——
在用例体内用 `try/finally` 兜住，无论成败都拆树。
同一个变异再跑：**只有 `until` 一条红，3 秒**。

> 顺带记一条踩过的坑：**不能用 `addTearDown`**。
> `AutomatedTestWidgetsFlutterBinding` 的 `!timersPending` 断言
> 在用例体一结束就跑，排在 tearDown **前面**，
> 于是每条用例都会报「A Timer is still pending even after
> the widget tree was disposed」。收尾必须发生在用例体**之内**。

### 1.8 `setSurfaceSize` 改的是画布，不是 `MediaQuery`

全部 widget 测试都写着

```dart
await tester.binding.setSurfaceSize(const Size(390, 844));
```

读起来像「在一台 390×844 的手机上跑」。**它只改渲染视口。**
`MediaQuery` 是从 `tester.view` 来的，而那个还是测试默认的
2400×1800 @3.0 = **800×600 横屏**。

于是应用按 390×844 布局，而任何按 `MediaQuery` 的尺寸或朝向分支的东西
都走另一条分支 —— 而且**布局本身看不出任何异常**：不溢出、不报错、
golden 也照样对得上，因为我们自己的组件不看 `MediaQuery`。

暴露它的是 Material 的时间选择器：它按朝向选版式，拿到「横屏」之后
用了 528dp 宽的横版，「确定」落在 x≈424，而屏幕只有 390 宽。
点不着。而失败信息说的是**「保存之后页面还在」**——
离真正的原因隔着三层：点没中 → 对话框没关 → 保存点在遮罩上 → 没落库。

> **判据**：凡是「把测试环境配置成某种样子」的调用，都要问一句
> **谁读得到这个配置**。改了渲染视口而没改 `MediaQuery`，
> 等于只把布景换了，演员手里的剧本还是旧的。

改法是 `test/support/app_harness.dart` 的 `setScreenSize()`：两处一起设，
并把 dpr 设成 1，省得每次都要想「390 是逻辑像素还是物理像素」。

## 2. 测试金字塔与责任划分

```
                  ▲  integration_test/   真机 / 模拟器端到端
                 ╱ ╲   少量、覆盖关键旅程（新增任务→看见→提醒）
                ╱   ╲
               ╱     ╲ test/presentation/ + test/golden/
              ╱       ╲  Widget 行为 + 视觉回归
             ╱         ╲
            ╱           ╲ test/application/  UseCase 编排
           ╱             ╲
          ╱               ╲ test/data/  Drift 真实内存库（不 mock DB）
         ╱                 ╲
        ╱───────────────────╲ test/domain/  纯 Dart，最厚的一层
```

| 层 | 用什么 | 不用什么 |
|---|---|---|
| `test/domain/` | 纯函数、值对象、真实实现 | **零 mock**（领域层没有依赖，无可 mock） |
| `test/data/` | **真实 SQLite 内存库**（`NativeDatabase.memory()`） | 不 mock DAO —— mock 掉数据库就测不出 SQL 写错 |
| `test/application/` | 真实领域层 + Fake 仓储（手写，非 mock 框架） | 少用 mocktail 的 `verify`，多断言最终状态 |
| `test/presentation/` | `ProviderScope` override 注入 Fake | 不打桩 Widget 内部 |
| `integration_test/` | 真实全栈 | — |

### 2.1 为什么数据层坚持用真实 SQLite

Drift 支持 `NativeDatabase.memory()`，跑得比 mock 只慢一点，但能抓到：外键约束、唯一索引冲突、
SQL 语法错误、事务回滚行为、迁移脚本错误。这些恰恰是 mock 永远抓不到、而线上一定会炸的东西。

> ✅ **已实测确认可行**（2026-09-07）：`flutter test` 在本机 Windows 宿主上直接跑通
> `NativeDatabase.memory()`，报告 SQLite **3.53.4**，**不需要 Visual Studio C++ 组件**。
> 验证方式不只是「跑通」——测试里故意插入重复主键并断言抛出 `SqliteException`，
> 确认这是真的 SQL 引擎在执行约束，而不是一个什么都接受的桩。

## 3. 执行机制：怎么保证上面这些不是口号

### 3.1 变异演练（Mutation Drill）—— 核心机制

每个里程碑结束时，对**关键模块**做一次变异演练：

1. 从下表挑选变异算子，手工改坏实现（改一处，跑全量测试，还原）。
2. 记录「哪些变异没被任何测试抓到」。
3. **每个存活的变异必须补一条测试**，或书面说明为什么可以放过。
4. 结果记入 `docs/05-engineering/mutation-drills/M{n}.md`，入库。

| 变异算子 | 具体做法 |
|---|---|
| 边界移位 | `<` ↔ `<=`，`>` ↔ `>=` |
| 常量篡改 | `0` → `1`，`30` → `31` |
| 条件反转 | `if (x)` → `if (!x)` |
| 返回值替换 | 返回空列表 / null / 默认值 |
| 语句删除 | 删掉一次赋值、一次 `await`、一次事务提交 |
| 顺序调换 | 交换两条相邻语句 |
| 异常吞掉 | 把 `throw` 改成 `return` |

**强制变异演练的模块**（这些地方出错用户会直接受损）：

- 重复引擎（`domain/recurrence/`）
- 状态机（`domain/policies/`）
- 时间换算（`core/time/`）
- 同步信封与 outbox 写入（`data/outbox/`）
- 导入导出往返（`data/dto/`）
- **守卫与校验工具本身**（`test/architecture/`、`tool/`）——
  它们出错不会伤到用户，但会让**所有依赖它们的结论一起失去意义**，且没有任何迹象。
  §1.4.1 就是这条的由来。

### 3.2 反向测试优先（Red-First）

**任何 bug 修复的第一个提交必须是「一条会红的测试」**，第二个提交才是修复。
PR 里能看到测试从红变绿。这条由 code review 检查。

### 3.3 CI 门禁

| 门禁 | 阈值 | 失败后果 |
|---|---|---|
| 全量测试通过 | 100% | 阻止合并 |
| 领域层行覆盖率 | ≥ 90% | 阻止合并 |
| 数据层行覆盖率 | ≥ 80% | 阻止合并 |
| 整体行覆盖率 | ≥ 70% | 警告 |
| 分层依赖守卫 | 0 违规 | 阻止合并 |
| `dart analyze` | 0 error、0 warning | 阻止合并 |
| 重复引擎基准 | 展开 1 年 ≤ 50ms | 阻止合并 |
| 无断言测试扫描 | 0 处 | 阻止合并 |

> **覆盖率是必要条件不是充分条件**。90% 覆盖率的重言测试依然一文不值。
> 覆盖率门禁的真正作用是防止「新代码完全没测试」，杀死坏测试靠 §3.1 的变异演练。

### 3.4 自动化的坏测试扫描

[`tool/lint_tests.dart`](../../tool/lint_tests.dart)（**已实现**，M0 交付）在 CI 中运行，
扫描 `test/` 与 `integration_test/` 并报错：

- 测试函数体内没有任何 `expect(` / `expectLater(`
- 出现 `if (Platform.` 或 `if (kIsWeb)` 形式的静默跳过
- 出现被注释掉的 `expect(`
- `skip:` 参数未附带说明字符串

它管的**只有一件事：这条测试有没有可能变红**。测试写得好不好靠 §3.1 的变异演练与评审。

按 §1.4，它自带 `--self-test`（手写坏样本 + 手写期望，不由被测函数产生），
且已对真实仓库演示过失败：注入无断言测试后 `exit=1` 并逐条定位，还原后 `exit=0`。

> 它刻意不引入 analyzer 包做完整 AST 解析 —— 要抓的几类问题都是词法层面可见的，
> 而 CI 需要它跑得快。代价是对极端排版可能漏判，**这一点写在脚本注释里，
> 而不是假装它是完备的**。

## 4. 时间相关测试的特殊纪律

时间是本项目最大的 bug 温床，也是最容易写出永远绿测试的地方。

1. **禁止真实时钟**。所有测试注入 `FixedClock` 或 `fake_async`。
   守卫扫描：`test/` 下出现 `DateTime.now()` 即报错。
2. **必须跨时区跑**。关键测试集参数化在 `Asia/Shanghai`、`America/New_York`（有 DST）、
   `UTC`、`Pacific/Kiritimati`（UTC+14）四个时区各跑一遍。
3. **必须覆盖 §边界**：闰年 2/29、月末 29/30/31、DST 跳表与回拨、跨年、跨时区迁移。
   完整清单见[重复引擎](../02-domain/recurrence-engine.md) §6。

## 5. 黄金用例表（Golden Cases）

领域层的核心行为用**表驱动测试**，用例表与期望值**写在文档里**，测试代码只是读表执行：

| 表 | 位置 | 条目数（V1 目标） |
|---|---|---|
| 重复展开 | [重复引擎 §6](../02-domain/recurrence-engine.md) | ≥ 30 |
| 状态迁移 | [任务生命周期 §7](../02-domain/task-lifecycle.md) | ≥ 25（含全部非法迁移） |
| 时间换算 | [横切关注点 §1](../01-architecture/cross-cutting.md) | ≥ 20 |
| 导入导出往返 | [数据模型 §6](../02-domain/data-model.md) | ≥ 10 |

好处：期望值经过文档评审，而不是「作者跑一遍抄下来的」。

## 6. 架构守卫测试

`test/architecture/layer_dependency_test.dart` 解析 `lib/**/*.dart` 的 import，断言
[模块与目录规范](../01-architecture/module-map.md) §3 的依赖规则。额外守卫：

| 守卫 | 断言 |
|---|---|
| 领域层纯净 | `lib/domain/**` 不含 `package:flutter/` |
| 写路径唯一 | `lib/features/*/presentation/**` 不 import `domain/repositories/` |
| 时钟注入 | `lib/domain/**` 与 `lib/features/*/application/**` 不含 `DateTime.now()` |
| 软删除不遗漏 | 所有 DAO 查询方法经由带 `deletedAt IS NULL` 的基类（用生成代码检查） |
| 命令可序列化 | 每个 `TaskCommand` 子类都有 JSON 往返测试 |

## 7. 视觉回归与布局约束（两类，必须用机制分开）

- 覆盖设计系统的基础组件 + 四视图的典型状态（空态、单条、密集、超长文本）。
- **明暗主题 × 三个字号档位**（有效缩放 1.0 / 2.0 / **2.8**，
  见[设计系统 §3.4](../03-design/design-system.md#34-缩放是两层相乘golden-必须覆盖到实际最坏值)）。
- golden 更新必须单独提交，PR 描述说明「为什么视觉变了」。
  **禁止**在功能 PR 里顺手 `--update-goldens`。

### 7.1 「断言型」与「快照型」必须用**机制**分开，不是用命名

无障碍与布局的检查很容易写成这样：给「2.8 下标题不被截断」拍一张 golden 图，
注释里标上「这是断言，不是快照」。

**标签不改变它变红的条件。** 拿图去比的东西就是快照 ——
让它红的仍然是「任何像素变了」，改一个间距 token 照样全红。
于是「改个间距 8 张图全红 → 无脑 `--update-goldens`」，
快照与断言在同一次操作里一起失效。

| | 断言型 | 快照型 |
|---|---|---|
| 产出 | **不产出图片** | 一张图 |
| 断的是 | 布局**约束** | 外观 |
| 改间距 token | **不该红** | 就该红 |
| 红了怎么办 | 布局真的破了，去修 | 人看图确认是否有意 |

断言型在 Flutter 里的写法是查渲染树，不是比像素：

| 要断的事 | 怎么断 |
|---|---|
| 标题不被截断 | 查 `RenderParagraph` 的 `didExceedMaxLines` |
| 操作区不出屏 | `tester.getRect(finder)` 落在视口内 |
| 触控目标 ≥ 48dp | `tester.getSize(finder)` 的两边都 ≥ 48 |
| 文本不溢出容器 | 无 `RenderFlex overflow` 异常 |

### 7.1.1 第三类：保护「实现选择」的对照组

§7.1 的两类都在保护**断言**。还有一类东西没人保护：**一个看起来可以
随便换的实现细节**。

具体案例（`design/tokens/contrast.dart` 的 `deriveGraphicColor`）：

| 写法 | 结果 |
|---|---|
| 先量化成 8 位色**再**判定是否达标 | 全空间 0 例越界 |
| 在浮点上判定、**最后**才量化 | 约一半输出越界 |

两者在 diff 上只差两行的位置。没有任何断言会因为换回后者而变红 ——
因为「输出达标」这条断言在两种写法下**都能通过**（后者的失败是概率性的，
而全空间枚举下才显形）。

**做法：写一个会红的对照组。** 把错误写法实现出来，跑同一批输入，
断言它**确实**产生越界；同时断言生产实现 0 越界。

于是：

| 问题 | 保护对象 |
|---|---|
| §9 第 4 条「这条断言在什么改动下会红」 | 断言 |
| **「这个实现选择换成什么写法会坏」** | 实现细节 |

判据：如果一段代码带着「必须这样写」的注释，而**没有任何测试会因为
换成另一种写法而变红**，那句注释迟早会被人合理地删掉。
对照组是把注释变成可执行的唯一办法。

### 7.2 怎么验证这两类**真的**分开了

不靠读代码，靠一次可复跑的操作：

> 拿一个**只改间距 token**的提交跑全部测试 ——
> **断言型必须全绿，快照型必须全红**。

任何一边不符合，说明没分开：断言型有红的 → 它其实是快照；
快照型有绿的 → 它没覆盖到那个 token。

这是 §3.2「反向测试优先」在视觉层的具体形式，也是
[评审要点 §9 第 4 条](conventions.md#9-评审要点按重要性排序)
（「这条断言在什么改动下会红」）唯一能落到实处的答法。

### 7.3 第三类之外：**用法级**对比度守卫

§7.1 分的是「断言型 / 快照型」，7.1.1 加了对照组。任务卡片做完之后又出现
一类它们三个都盖不住的东西。

[design-system §10](../03-design/design-system.md) 那套穷举守卫验的是
**token 本身**：`brand.primary.text` 对三个亮表面 ≥4.5，全空间验过。
但 token 达标 ≠ **用对了地方**。把 `brand.primary.graphic`（3.46，图形级）
拿去当标签色，两个 token 都合规，渲染出来的界面不合规 ——
守卫看不见，因为它压根不知道谁被用在了哪。

于是加一层：`test/design/token_usage_test.dart`。做法是
**渲染组件，遍历渲染树，把每段文字与它真正压着的背景配对，算对比度**。

它和「扫源码找 `brandGraphic` 出现在 `TextStyle.color` 位置」的区别是本质的：

| | 扫源码 | 遍历渲染树 |
|---|---|---|
| `colors.brandGraphic` | 抓得到 | 抓得到 |
| `const Color(0xFF379986)` | 抓不到 | 抓得到 |
| 中间变量传进来的 | 抓不到 | 抓得到 |
| 主题 lerp 出来的中间色 | 不存在这个概念 | 抓得到 |
| 半透明叠加后的实际观感 | 抓不到 | 合成后再判 |

守的是「文字压在背景上」这个**几何事实**，不是变量名的拼写。

**第一次跑就抓到一个已经全绿的缺陷。** 任务卡片的已完成标题用了
`border.subtle`（`#EDE7DD`，发丝分隔线的颜色）当文字色，实测 **1.23:1**。
当时断言型 32 条、快照型 6 张全绿，而且**人看过那张 golden**，
把「淡到读不出」读成了「完成态变淡，符合预期」。

这条值得单独记下来，因为它说明**看图确认不是验证**：
人眼看「淡」和仪器量「1.23:1」是两件事，而只有后者能判「读不读得出」。
快照型测试的价值在于「变了会红」，不在于「人看着还行」。

配套的两条纪律：

1. 门槛不放宽。WCAG 允许大字号降到 3.0，这里**不做这个豁免** ——
   §10 定的谓词里没有它。真撞上，去改文档里的谓词，不在测试里开口子。
2. 守卫必须先被证明能失败（§1.4）。文件里前三条就是自检：
   故意用 `graphic` 当文字色必须红、换成 `text` 必须绿、
   半透明背景必须合成后再判。

**新增组件必须加进那个画廊** —— 这一层只覆盖它渲染得到的东西。
