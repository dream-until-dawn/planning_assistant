## M4 为什么能逃掉

**因为当时全部 DST 用例都用 `America/New_York`，那是个负偏移时区。**

| 偏移方向 | 真实绝对时刻相对「把墙钟当成 UTC」的位置 |
|---|---|
| 负偏移（`America/New_York` −5/−4） | **之后** |
| 正偏移（`Australia/Sydney` +10/+11） | **之前** |

搜索窗口左端缩掉后，正偏移时区的真实时刻落到窗外，`offsetLo` 取到的是跳变**之后**
的偏移，于是走进「窗口内无跳变」分支并抛 `StateError`。而负偏移的样本全程不碰左端，
所以 8 条 DST 用例一条都没红。

**这不是「样本不够多」，是样本在一个维度上系统性地偏了** ——
所有 DST 样本都来自同一个半球、同一个偏移方向。与
[testing-strategy §1.3](../testing-strategy.md) 记的 freezed 那次同源：
「我手上恰好有的数据」不等于「能支撑结论的样本集」。

## 顺带记一笔：实现本身也被打回过一次

`resolve()` 初版用「在绝对时刻上二分『当地时间 ≥ 目标』」，秋季回拨用例当场变红 ——
**当地墙钟在 UTC 上不是单调的**，01:00–01:59 会出现两次，二分的前提不成立。
春季跳表恰好单调，所以那组过了、这组没过。

改成「候选偏移 + 二分找跳变点」后两组都过。这段经过写进了 `resolve()` 的文档注释，
避免将来有人觉得二分更简洁而改回去。

## 第二轮：兄弟会话评审提出 3 条，全部复现属实

M1-A 自评通过后送外部评审，回来 3 条。按工作原则第 4 条**先自己复现**，
结果三条都成立 —— 记录在此，重点不是「被抓到了」，而是**我们自己的测试为什么没抓到**。

### B1 二分只收敛到 1 分钟 → instant 最多偏 60 秒

`resolve()` 里找 DST 跳变点的二分停在 `b - a > 60000`，
循环不变式是「真实跳变点 T ∈ (a, b]」，所以 `b` 最多比 T 晚 60 秒。
墙钟落进 DST 空隙时直接返回 `transitionMs`，误差就进了 Instant：

```
02:00 → 2026-03-08T07:00:14.062Z     02:30 → 2026-03-08T07:00:00.000Z
02:01 → 2026-03-08T07:00:31.875Z     02:45 → 2026-03-08T07:00:14.062Z
02:15 → 2026-03-08T07:00:28.125Z     02:59 → 2026-03-08T07:00:10.312Z
```

**为什么第一轮没抓到 —— 两层原因，第二层更值得记：**

1. 断言 instant 的用例只挑了 `02:30`，而它恰好是空隙里唯一收敛精确的输入
   （目标恰在二分中点上）。「整段空隙都顺延到 03:00」那条用例断的是
   `effectiveWallTime`，截到分钟，误差被吃掉了。
2. **R-09d 的往返恒等 `untilForExpansion(untilForStorage(w)) == w` 结构上测不出精度问题** ——
   `untilForExpansion` 要截到分钟，往返把误差整个吸收。
   这条教训比 bug 本身值钱：**往返恒等验的是「两个方向互逆」，不是「值对」。**

修法：`while (b - a > 1)`，收敛到毫秒。多约 16 次迭代。

### B2 `tz.local` 从未设置 → `currentZoneId()` 恒为 `Etc/UTC`

`initializeTimeZones()` 只加载数据库、**不设置 `tz.local`**。缺 `setLocalLocation()` 时
`tz.local.name` 恒为 `Etc/UTC`，北京用户设的「每天 07:00」被记成 UTC 07:00 = 当地 15:00。
**完全静默，不抛异常** —— 正是 ADR-0005 要防的那个 bug。

第一轮没抓到，是因为唯一一条 `currentZoneId` 用例注入了 `fixedCurrentZoneId`，
把真实路径整个绕过去了。**注入替身时要留一条走真实路径的用例。**

修法：`setUpLocalTimeZone()` + `PlatformTimeZoneSource` + `MainActivity.kt` 的 MethodChannel。

### S1 旧式时区别名直接抛异常

实测 `latest.dart` 数据库里 `UTC` / `GMT` / `Asia/Calcutta` **都不存在**。
Android 至今大量设备报这些值 → 该设备上每条任务都无法换算。
修法：`_zoneAliases` 表 + `UnknownTimeZoneException`（不静默降级）。

## 引入差分测试（`test/core/time_zone_differential_test.dart`）

评审方的建议，事后看是这一轮里最值钱的一条。

oracle 用**暴力扫描**独立实现「当地墙钟 ≥ W 的最小 epoch」，不共用被测逻辑。
12 个按行为特征挑的时区 × 35 个日期 × 12 个时刻 = **4896 组**。

把 B1 改回 1 分钟收敛，差分测试报 **14 组不一致**，覆盖 5 个时区
（New_York / Dublin / Sydney / Lord_Howe / Santiago）—— 而手写用例表只覆盖了其中 2 个。

同时加了一条不变式：**`resolve()` 的 instant 必须落在整分钟边界上**。
输入是分钟粒度，输出就不该带秒。这条不依赖「猜到问题出在二分精度」，
**防的是一类而不是一次**。改回 1 分钟收敛时，该文件 4 条测试全红（0 通过 / 4 失败）。

## 一条差点写成「永远绿」的测试

B1 会经 `untilForStorage()` 渗到领域层：`untilForEndDate` 会产出
`23:59:09.312 + 59s` 这样的垃圾 UNTIL。于是在 `recurrence_engine_test.dart` 加了
「UNTIL 恒为 `:59.000`」的不变式。

第一版挑了 New_York / Sydney / Santiago —— **把 B1 改回去，它不红**。
因为 `untilForEndDate` 取的是 23:59，而这些时区的跳变都在凌晨，
23:59 永远存在，**走不到出问题的那个分支**。那就是一条永远绿的测试。

于是扫了整个 tz 数据库（1970–2037 共 **8846 次**春季跳变），
问「有没有哪个 (时区, 日期) 让 23:59 不存在」：**命中 47 条**。
格陵兰的 `America/Nuuk` 与 `America/Scoresbysund` 自 2024 年起在 UTC 22:00 跳变，
当地 **23:00–23:59 整段消失**。用户在那儿设「每天重复，到 3 月 28 日止」就会踩中。

换成 Nuuk 后重新注入 B1：

```
4 处 UNTIL 不在秒边界上：
  America/Nuuk 2026-03-28 → 2026-03-29 01:01:09.312Z
  America/Nuuk 2027-03-27 → 2027-03-28 01:01:09.312Z
  America/Scoresbysund 2026-03-28 → 2026-03-29 01:01:09.312Z
  America/Scoresbysund 2027-03-27 → 2027-03-28 01:01:09.312Z
```

**教训：写完不变式必须注入缺陷验证它会红。**「看起来在测边界」和「真的能红」
之间隔着一整个 tz 数据库扫描。这正是工作原则第 3 条「永远绿的测试等于没有测试」
最具体的一次体现 —— 它不只针对显然的假测试，也针对**看着很像真测试的那种**。
